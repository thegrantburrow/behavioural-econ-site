# Live Interactive Session

## Why this exists

Founded 2026-08-28 on a direct request: build a real, live, in-person demonstration of anchoring, two QR codes seeding two different anchors before the same estimate question, run with a real audience during a real talk, results shown live in the room. The owner's own framing: "New category of the website. These will be illustrative interactive sessions where an audience will experience behavioural science and economics in action." Anchoring was the pilot; more are expected to follow the same standard. This skill exists so the next one (loss aversion, social proof, whatever comes next) starts from the pipeline and the real technical lessons below, instead of re-deriving them.

**The pilot went through two real builds, not one, and the second is the one to copy.** The first build used a Claude Artifact's shared-state `publish()` capability to get a genuinely live, auto-updating results screen across every phone in the room. It worked (verified across multiple republish generations), but it meant participants landed on `claude.ai`, needed the artifact link to actually be shared with write access (an open question that was never confirmed), and depended on a platform outside this site entirely. When asked directly, the owner chose independence from Claude over the live auto-sync: "I need to be able to see them independent of Claude. Enable this." Faced with the explicit tradeoff (own site with no login prompt and no platform dependency, vs. live cross-device tally that only works on claude.ai), he picked the former. **Default to the static, no-backend build below for the next session in this category, and only reach for the Claude Artifact approach (kept further down for reference) if a future request explicitly asks for live cross-device sync and explicitly accepts the claude.ai dependency that comes with it.**

## What this content type is, and isn't

It's a **live, in-person replication of a real published paradigm**, run with an actual audience, not a read-only page and not a hypothetical. It's distinct from every other content type on this site: `behavioural-principle-article` explains a mechanism from its cited study; `experiment-blueprint` is a testable design nobody has run yet; `field-session` is a first-person recap of a talk after it happened. A Live Session is a tool people actually use, during the talk, and the "content" (the write-up, the citation, the framing) exists to support that live moment, not to stand alone. It shares one discipline with every other content type on the site: the paradigm has to be a real one from the literature, not an invented "fun fact" quiz.

## The pipeline, in order

1. **Pick a principle already on the site with a real, replicable lab paradigm**, not just a mechanism that's true in general. Anchoring works because Tversky & Kahneman (1974) is a clean two-step design (comparative judgment against a planted anchor, then a free estimate) that transfers directly to a phone screen. Not every principle transfers this cleanly, check whether the actual published methodology is something a room full of people can do in under a minute before committing to it.
2. **Design the paradigm faithfully**, not just "in the spirit of" the study:
   - A comparative judgment against the anchor ("more or less than X?") always comes before the free estimate, this is the real two-step design from Jacowitz & Kahneman (1995) and the original 1974 study, not a detail to drop for simplicity.
   - Use the real historical anchor values when the study you're replicating had specific ones (10 and 65 for the UN-Africa question), don't invent round numbers that feel plausible.
   - Assignment to condition has to be effectively blind and effectively random from the participant's side. Two QR codes that look identical (same design, same size, no visible label reading "A" or "B") satisfy this even though the underlying links differ, what matters is nothing on the page or in the room ever tells a participant which condition they're in.
   - Report the group gap as a **median**, not a mean, these estimate distributions are typically right-skewed and a mean gets pulled by outliers.
3. **Build it as a plain page on the site itself** (see "The default build" below), not a Claude Artifact, unless live cross-device sync has been explicitly requested and the claude.ai dependency explicitly accepted.
4. **Generate real QR codes pointing at the deployed page's URL**, one per condition, plus one for the presenter's tally/reveal view, using the site's own domain. Verify each one actually decodes to the intended URL with a real decoder before treating it as done, a QR code that looks right and doesn't scan right is worse than no QR code. Regenerate and re-verify them any time the hosting decision changes, a QR made for one URL is dead weight once the tool moves.
5. **Wire it into `live-sessions.html`** (or whichever page holds this category): the paradigm explained in plain language, real "try it yourself" links for someone browsing the site outside a live event, a cross-link to the full principle article for the citation and methodology critique, and a plain, honest explanation of how the room's results actually get compared (see below, this isn't automatic in the default build). Add the nav entry, footer link, sitemap entry, and homepage `explore-hub-card` the same way every other new category on this site gets wired in, that's not optional polish, it's how the category is actually reachable.

## The default build: fully static, no backend, persisted per device via localStorage

`grantburrow.com` has no backend and no database. The honest, fully-independent version of a "live" session accepts that a phone's individual answer has no way to travel to another phone or to a projector screen on its own, and designs around that instead of fighting it. It went through one real revision here too: the first pass kept the tally in a plain JS variable that vanished on reload, which surfaced two real gaps the moment the owner actually used it (see "Two real gaps found by actual use" below). The fix, now the default, uses `localStorage` as a genuine append-only log, not just an in-memory array:

- **The participant page** (`anchoring-live.html` for the pilot) is one plain HTML file, no external dependencies, reading which condition to show from a URL hash (`#g=a` / `#g=b`, never a query string, since a hash is guaranteed to work identically regardless of how the link reaches the browser and is never sent to any server). It runs the comparative question, then the estimate, then a thank-you screen. On submit, the answer is appended to the same `localStorage` log the results screen reads (see below), so if the participant and the results screen happen to share a browser (the owner's own testing, a shared kiosk device), it shows up automatically with no extra step. The thank-you screen still tells the participant plainly what to do for the real multi-phone case: **call out your number, or put your hand up, when the room compares notes**, since separate physical phones can never share `localStorage` with each other, only a shared backend could do that, and this build deliberately doesn't have one.
- **The log is a single append-only array in `localStorage`** (`{id, g, v, t, sessionId}` per entry), plus a small pointer to the *current session* (`{id, startedAt}`). Every entry, whether it arrived from a participant's own submission or the presenter typing in a called-out number, goes through the same `addEntry(group, value)` function into the same log, so the live tally is genuinely just "every logged entry belonging to the current session," not two separate code paths that can drift apart.
- **"Start new session" advances the session pointer, it never deletes anything.** The live tally and chart are filtered to the current session's id, so clicking it makes the numbers on screen go back to zero, but every prior session's entries stay in the log, groupable and viewable in a history table (date, time, group, per-entry value, an individual delete button). This is what actually satisfies "reset results for a new talk" and "keep a dated log" as the same feature instead of two competing ones.
- **A separate, more serious "clear all history" control** wipes the entire log and starts a fresh session, confirmed with the real entry count in the prompt ("permanently delete all 47 recorded answers"). Keep this visually and functionally distinct from "start new session", one is routine (used before every talk), the other is destructive and rare.
- Show the real fact's true answer as a marked reference line on the chart, and where the paradigm you're replicating has real published numbers (Tversky & Kahneman's own 45%/25% medians), show those too, clearly labelled as the original study's result, not this room's.

This gets you a real, live-feeling results reveal (the presenter types or a same-device phone submits, the bar chart moves, right there on the projector), a genuine dated record across many separate talks, and a real reset, all without a login, a platform dependency, or a backend.

## Two real gaps found by actual use, not by re-reading the spec

The first `localStorage`-free version of this build was reviewed, tested with Playwright, and shipped looking complete. It wasn't. The owner actually used it (entered one estimate on the Group A link, one on Group B) and reported: "Results didn't come. Nor did a QR code come up." Two separate, real gaps, neither of which a code review would have caught because the code did exactly what it was written to do, it just wasn't written to do enough:

1. **An in-memory-only tally can't show a participant's answer on any other screen, not even the same device's own results tab, because a fresh page load starts a brand new, empty JS variable.** The fix (this skill's default now) is to back the tally with `localStorage`, which persists across page loads and, load-bearing, is shared across every tab of the same browser on the same device. Test this for real the way the gap was actually found: submit an answer in one tab, open the results view in a second tab of the *same browser context*, confirm it appears, don't just trust that "no backend" was correctly implemented as "no persistence at all."
2. **Sending QR code images to the owner once, in chat, is not the same as the tool being able to produce them.** "Generate QR code for each when I start a session" was a real, reasonable ask: the results screen itself should show the codes, every time it's opened, not require a separate message asking for them again. Since the two participant URLs (`#g=a`, `#g=b`) never change between sessions, this doesn't need live QR generation, pre-render the two PNGs once (Python's `qrcode` library, verified against a real decoder, same as the printable copies), save them into `mockup/images/`, and have the results screen `<img>` them inline. Client-side JS QR generation was considered and rejected here specifically because this environment's CDN allowlist doesn't reliably reach arbitrary JS library hosts, a pre-rendered static image has no such dependency and is simpler besides.

## A real CSS trap: flex-centering a child that isn't a flex parent

The participant screens center content using `.screen { flex: 1; justify-content: center; }`. The first pass rendered pinned to the top instead. Root cause: `.screen`'s actual parent was a plain `<div id="app">` (re-rendered via `innerHTML`/`appendChild` on every screen change), and `#app` itself was NOT `display: flex`, so `.screen`'s own `flex: 1` had nothing to size against. The fix is one line, `#app { display: flex; flex-direction: column; flex: 1; min-height: 0; }`, but it's the kind of bug that looks fine in the markup and only shows up on an actual screenshot. Screenshot every screen at a real mobile width before calling a live-session tool built, don't just read the CSS and assume it centers.

## Don't rely on a platform's own share dialog to hand out per-view links

A real point of confusion in this pilot: the owner opened the artifact's own "Share" menu (Rename / Duplicate / Share / Version history, standard claude.ai chrome) expecting it to hand him a QR code for the specific view he wanted (Group A, Group B, or the reveal screen). A platform share dialog shares the canonical resource, it has no reason to know about a URL fragment like `#g=a` that only your own page's JavaScript understands. **Always generate and verify your own QR codes and plain-text links for each specific view your tool defines**, pointing at the exact full URL including whatever hash or parameter selects that view, and never assume a generic "Share" button will do this for you.

## The reveal screen needs a self-contained narrative, not just a chart

**What happened.** The Anchoring pilot's reveal screen shipped with a bar chart and a static historical-comparison line, but nothing telling the presenter (or anyone who screenshots the page later) what their specific numbers meant, whether this room's result actually replicated the classic effect, what the mechanism actually is, or where it shows up outside the room. The owner's request, verbatim: "This page below the answers should have a full narrative write up... using the results shown. Aka if they align to the anchoring and if they don't... mitigates by using as an interactive lesson eg sometimes noise in context can influence replication etc." A chart alone makes the reader do all the interpretation themselves; a live tool that already has the real numbers in hand should do that interpretation for them, every time it re-renders.

**The fix, in practice.** A `renderNarrative()` block, computed fresh on every render from the actual `byGroup` data (so it updates live as answers are added or removed), with three parts:
1. **A verdict that branches on the actual comparison**, not a fixed message: no data yet, one side still empty, medians tied, the classic direction (high anchor's median above low anchor's), or the reversed direction. Each branch is written for what it is, not as a generic "results may vary" hedge. The reversed branch is the one that matters most: it explicitly reassures that a single small room reversing the effect doesn't undo a well-replicated finding, names the real reason (noise, small per-group samples), and turns it into the stated lesson, that a single small study or session should never settle a question the way a large replication does, cross-linking to this site's own `small-sample-big-claim.html` report rather than just asserting it. A small-n caveat is added even to the aligned branch, so a real replication in a small room doesn't get oversold as more conclusive than it is.
2. **A self-contained mechanism paragraph**, written so a reader who lands on this exact page with zero other context (no principles.html visit, no session introduction) still gets the real explanation, matching the language already established on `principles.html#anchoring` (the anchoring-and-adjustment heuristic, adjustment stopping too early), with a link onward for the full write-up rather than duplicating it at length.
3. **Real, cited, relatable examples of the mechanism outside the room.** Five, each independently WebSearch-verified before writing (author, year, journal): credit card minimum repayments (Stewart, 2009), real estate listing-price anchoring on professional appraisers (Northcraft & Neale, 1987), first-offer advantage in negotiation (Galinsky & Mussweiler, 2001), judges' sentencing decisions anchored by a die roll (Englich, Mussweiler & Strack, 2006), and social-security-digit anchoring on auction bids (Ariely, Loewenstein & Prelec, 2003). Picking examples that are genuinely anchoring, not an adjacent mechanism (decoy pricing, framing, scarcity) that merely feels related, matters as much here as it does in `science-behind-article`'s own mismatched-mechanism failure mode.

**The check.** Verify every branch actually renders, not just the happy path: seed `localStorage` directly (via Playwright's `page.evaluate`, then `page.reload()`, not `page.goto()` again, since a second `goto` can race the reload before the seeded data is read) with empty, one-sided, aligned, tied, and reversed data, and screenshot each. A tool whose whole point is showing real-time results needs its interpretation layer tested across the actual range of results it can produce, not just the one the developer happened to type in first.

## The reveal screen is projected on a wall, design for that distance, not for a phone

**What happened.** The pilot's reveal screen (and the 5 tools that copied its structure) used the same type scale as the participant screens, 12-16px body text, a 26px-tall bar chart, a 28px median number, because nothing distinguished "a screen someone reads up close" from "a screen a room reads from the back row." The owner's catch, verbatim, pointing at the live URL: "Results page should be Much More visually engaging with example and visualisation like we've built imagine on a large screen with a room." A page sized for a phone doesn't scale up into a good projector screen just because a browser can zoom, the whole information hierarchy needs to change: one or two numbers matter at a glance, everything else is secondary.

**The fix, in practice.** The reveal screen is really two audiences sharing one URL, and the layout has to say so:

1. **A room-scale scoreboard is the single focal point**, not a chart among several. Two big cards, one per group, each showing that group's headline number at `clamp(52px,8.5vw,104px)`, Georgia, bold, big enough to read from the back of a room, with a small circular "VS" badge between them and an animated fill bar underneath (`width:0` at creation, set to the real percentage inside a `requestAnimationFrame` callback so the transition actually plays instead of snapping straight to its final state). A `scPop` keyframe (`scale(.7)&rarr;scale(1.07)&rarr;scale(1)`) on the number itself gives every re-render, a new answer coming in live, a visible "pop" rather than a silent DOM swap. A `.scoreboard-gap` line underneath states the actual gap in plain language ("40 percentage points apart between the two groups, same real question, same room"), doing the subtraction for the room instead of making people eyeball two bars.
2. **Presenter input controls get visually demoted, on purpose**, into a `.presenter-controls` box: dashed border, muted background, small type, an explicit "Presenter controls" eyebrow and a one-line note ("This box is for whoever is running the session, not for the projector"). The same input fields and choice buttons from before still work exactly the same, they just no longer compete with the big numbers for attention. Don't duplicate the big median/percentage inside this box too, once it's shown large in the scoreboard, repeating it here in small type is redundant, not reassuring.
3. **A historical comparison with real structured numbers** (a study's own high/low or A/B medians, not just a citation sentence) can become a second, smaller two-column mini-scoreboard in the same visual language, exactly like Anchoring's "This room vs. the original 1974 study" grid. A tool whose citation is prose-only (no clean paired numbers to chart, most of the 5 non-Anchoring tools) doesn't get a fabricated chart to force the parallel, it gets a plainly labelled `.historical-card` callout instead, bigger and better-framed than a bare paragraph, but honest about not having comparable structured data to plot.
4. **QR codes get bigger too** (`max-width:260px`, up from 200px), since a phone in the back of a real room has to resolve a projected code from several metres away, not just look tidy in a browser tab.

**The check.** Screenshot the scoreboard specifically (not just the full page) at a real large-display width (1600&times;1000 or wider, simulating a projector or a big screen, not just a phone), for the empty state, the aligned state, and the reversed state, and confirm the big numbers, the VS badge, and the gap line all read clearly at that scale before calling a redesign done. Re-check the participant screens and the full mobile reveal layout too, a redesign aimed at a room-scale audience has broken the phone-scale audience before if it isn't checked both ways.

## Build mobile-first, then adapt the reveal screen for desktop/billboard as a distinct mode, not just a bigger version of the same layout

**What happened.** The room-scale scoreboard fix above made the reveal screen's own content scale up nicely on a wide viewport (`clamp()`-based font sizes growing with `vw`), but it was still one continuous layout: the same presenter-input boxes, the same session-management row, the same long mechanism-and-examples read, just bigger. The owner's next request, verbatim: "this should be done distinctive for desktop / billboard vs mobile. Per our build, mobile optimised then ADAPT for desktop / billboard eg on desktop can toggle to say, ROOM PRESENTATION VIEW." The real distinction isn't screen size, it's *audience*: a phone is always the participant's own device, answering one question, so it never needs anything more than the existing compact flow. A desktop or laptop screen, on the other hand, plays two different roles at once, the presenter's own console (typing in called-out numbers, managing sessions, reading the full mechanism write-up) and, cast to a projector or a shared display, the room's own view of the results, and those two roles want opposite things from the same page: the console wants every control visible, the room wants nothing but the big numbers.

**The fix, in practice.** A single explicit mode toggle, "Room presentation view" (reads "Exit presentation view" once active), rendered as a `.session-btn.presentation-toggle` next to "Start new session" in the session row. It's desktop-only by construction, not by convention: `@media (max-width:760px){ .presentation-toggle{display:none;} }` removes the button entirely below that width, so a phone never even offers a mode it has no use for, that's the "mobile-first, then adapt" build order made literal, the mobile layout doesn't grow a feature it doesn't need, the desktop layout gains one on top of the shared base. Clicking it toggles a single `presenting` class on `document.body` (not on the per-render `#app` wrapper, since that gets torn down and rebuilt on every entry added or removed, a body-level class is the one piece of UI state that has to survive a re-render) and attempts `document.documentElement.requestFullscreen()`, wrapped in `.catch(function(){})` since fullscreen requires a user gesture and can be silently refused by the browser or an embedding context, that failure should never break the toggle itself. A single `fullscreenchange` listener, registered once at boot time (never inside `renderReveal()`, which runs on every add/remove/session-reset and would otherwise stack a duplicate listener per interaction), drops the `presenting` class automatically if the browser exits fullscreen on its own (the room's own Esc key, an OS-level interruption), so the page can't end up stuck half-hidden but no longer actually full-screen.

`body.presenting` then hides everything that's console-only, never content: give every presenter-facing control (the "Start new session" button, the session-started/answer-count readout) a `manage-only` class, and hide `.manage-only`, `.presenter-controls` (the input boxes/choice buttons for logging answers), `.narrative-block` (the mechanism explanation and the real-world examples, genuinely worth reading but not something to flash on a shared screen mid-session), `.history-section`, and `.reset-row` all at once. What's left, the QR codes (a late arrival still needs to scan in), the scoreboard, the gap line, the historical comparison, and the verdict box, gets a second, larger type scale on top of the scoreboard's own responsive sizing (`.scoreboard-number` up to `180px`, `.reveal-title` up to `68px`, the verdict's own text bumped too), because a screen that's finally free of console chrome can afford to spend all of that reclaimed space on making the two or three things that matter even bigger, not just less cluttered.

**The check.** For every tool, at a real projector-width viewport: click the toggle, confirm the button's own label flips, confirm `document.body.className` contains `presenting`, confirm `.presenter-controls`, `.history-section`, `.reset-row`, and every `.manage-only` element compute to `display:none`, and confirm no horizontal overflow appears at that width. Then load the same tool at a real mobile width and confirm `.presentation-toggle` computes to `display:none`, a phone should never be offered a mode meant for a shared screen it isn't. `requestFullscreen()` will typically be refused or a no-op under a headless test runner, that's expected and shouldn't be treated as a failure, the class-toggle and content-hiding behavior is what the check verifies, not whether the browser actually went full-screen.

**Rollout discipline.** This is exactly the kind of feature that has to land in the shared `live_template.html` generator, not be hand-patched onto one tool, since every non-pilot session (Framing, Decoy, Endowment, Present Bias, Compromise, Perceived Fairness, and whatever comes next) is generated from that one file. Add it to the template and the bespoke Anchoring pilot together, regenerate the whole batch, and spot-check the toggle on more than one regenerated tool, not just the one it was designed against, before calling the rollout done.

## A single button in an admin row doesn't read as a mode switch

**What happened.** The "Room presentation view" button above shipped and worked correctly, but the owner reported he couldn't find it at all: "I can't find in live sessions where to toggle mobile vs desktop vs presentation mode." The button was real, present on all 7 tools, and desktop-only exactly as designed, the problem was never that it didn't work, it was that nothing about how it looked said "this switches the page's mode." It sat in the `.session-row` at the same visual weight as "Start new session," a same-styled `.session-btn` among other same-styled `.session-btn`s, so a visitor scanning the row saw a row of admin actions, not a control worth stopping on. Presented with three concrete options (a floating pill, a segmented switch, or a hub-page callout plus a one-time pointer), the owner picked the segmented switch, rated "needs work" but with the instruction "Use this method," meaning the direction was right even if the first mockup wasn't the final polish.

**The check.** A toggle that changes the whole page's mode (not just one setting) needs to look categorically different from a same-row action button, not just be a differently-colored button in the same row. Ask: if a visitor covers every other button in the row and looks at just this one, does its shape alone say "pick one of two states," or does it read as "click to do a thing"? A pill-shaped button with a single label that changes text on click (the original design) is the second kind, it looks exactly like every other button until read closely.

**The fix, in practice.** Replaced the single button with a real two-segment switch (`.mode-switch`, "Standard" / "Presentation"), reusing the exact segmented-pill pattern `live-sessions.html` already uses for its own "By category / All 7" view toggle, so the control type itself is one visitors have already seen elsewhere on the site. Moved it out of the `.session-row` entirely and placed it as the very first element in `.reveal-wrap`, above the `.reveal-title`, so it's the first thing on the page rather than one item in a mid-page row. Clicking "Presentation" or "Standard" sets `document.body.classList` exactly as the old button did (`presenting` on/off, attempt `requestFullscreen`/`exitFullscreen`), so none of the existing `body.presenting` CSS or hide-on-presenting logic needed to change, only the control surface. The `fullscreenchange` listener that drops `presenting` when the room's browser exits fullscreen externally now also calls a `currentSyncModeSwitch()` reference (a module-scope function var, reassigned to the current render's `syncModeSwitch` closure each time `renderReveal()` runs) so the two segments' active states stay correct even when presentation mode ends via the Esc key rather than a click on either segment. Same `@media (max-width:760px){ .mode-switch{display:none;} }` rule as before, a phone still never sees a mode switch it has no use for.

**What this doesn't fix.** Moving the control and changing its shape only helps once someone has already opened a specific tool's results screen. Nothing on `live-sessions.html` itself mentions that presentation mode exists at all, so a visitor browsing the hub still has no way to know to look for it. That's a separate, real gap (the rejected Option 3 in this round addressed it directly, a hub-page badge plus a one-time pointer) worth revisiting if discoverability from the hub page specifically comes up again.

## The historical comparison is a second hero, not a footnote

**What happened.** The room-scale scoreboard fix treated the live head-to-head numbers as the page's one hero moment and left the "this room vs. the original study" comparison underneath it at its old, small type scale (11-14px labels, a 14px-tall bar), the same size it was before any of the room-scale work started. The owner's catch, circling that exact section on a phone screenshot: "These needs to be far bigger because they're kind of the hero?" He was right: the whole point of a live session is the room's own result held up against the classic finding, that comparison carries as much weight as the live scoreboard itself, not less.

**The fix, in practice.** Gave the historical comparison the same three-tier treatment as the scoreboard: a real base size increase (bar height from 14px to a `clamp(26px,3.4vw,44px)` range, row/label text roughly 30-40% larger, each side wrapped in its own bordered, shadowed card matching `.scoreboard-card`'s own visual weight rather than sitting as bare rows in a strip), further growth through the existing responsive `vw`-based `clamp()` scaling on a wide screen, and a third, largest step under `body.presenting` (bar height up to `58px`, row labels up to `24px`), exactly mirroring the scoreboard's own three-tier escalation. The prose-only version (`.historical-card`, used by every tool whose citation is a sentence rather than paired numbers) got the identical treatment in kind, not degree, no bar chart to enlarge, but the same jump in type size (body text from `13.5-15.5px` to `16-23px`, further to `20-30px` presenting) and card padding, so a tool without structured historical numbers still gets a second hero-weight moment, just one built from typography instead of bars.

**The check.** Whenever the scoreboard's own type scale changes, re-open the historical comparison specifically (not just the page as a whole) and ask whether it still reads as roughly comparable in visual weight, a component that was sized to feel appropriately secondary next to an old, smaller scoreboard can quietly become the one under-scaled element left on the page the next time the scoreboard itself grows. Screenshot `.historical` in isolation, the same discipline already used for the scoreboard, at mobile, plain desktop, and presenting width, before calling a scoreboard-scale change finished.

## The two QR codes stay side by side on mobile, they never stack

**What happened.** The Anchoring pilot's `.qr-grid` used a fixed `1fr 1fr` grid with its own `@media (max-width:520px){ grid-template-columns:1fr; }` override, a leftover from before the QR cards were sized up for room-scale visibility. The shared `live_template.html` used for every other tool never had that override, it used `repeat(auto-fit, minmax(150px, 1fr))`, which keeps two columns as long as two 150px-minimum tracks fit, comfortably true even at a 375-390px phone width. The result: Decoy (and every other template-based tool) showed its two QR codes side by side on a real phone, Anchoring alone stacked them into two full-width cards, a real, visible inconsistency between tools that are otherwise meant to be identical. The owner's catch, on a live phone screenshot circling Decoy's side-by-side pair as the one to match: "On mobile these are due by side but no for the anchoring... rollout consistently do side by side."

**The check.** Whenever the pilot (`anchoring-live.html`) and the shared template diverge on any shared component's CSS, that's not two legitimate variants, it's drift, the exact same trap the room-scale scoreboard and presentation-mode work already had to watch for elsewhere in this skill. Diff the two files' rules for the same class name (`.qr-grid`, `.scoreboard-*`, `.historical-*`, anything both files define) whenever either one gets touched, and treat any difference as a bug to resolve toward one canonical rule, not a per-tool style choice, until proven otherwise.

**The fix, in practice.** Removed Anchoring's `1fr 1fr` grid and its mobile-stacking override, replaced with the exact same `repeat(auto-fit, minmax(150px, 1fr))` rule the shared template already used, so there is now one canonical `.qr-grid` rule, not two independently-maintained ones. Verified at a real 390px mobile viewport: both codes render at 165px-wide columns side by side, no horizontal overflow, still comfortably scannable. Since the other six tools were already using the correct pattern, this was strictly a one-file fix, but the check above is the standing rule for next time a shared class gets edited in only one of the two source files.

## Step 1 needs a second filter: the task itself has to really happen live, not be imagined

**What happened.** The Endowment Effect tool passed every existing check in this skill (a real published paradigm, faithful two-group design, real citation) and still didn't work as a live session. Its participant screen read "Imagine you've just been given a mug as a gift" before asking for a selling price. The owner's catch, verbatim: "Endowment effect live session doesn't work. It's hypothetical... replace with s[ome]one that will work with live audience eg anchoring works because there is an actual live actual anchoring." He'd put his finger on something step 1 never actually asked: Anchoring's two groups really do see two different planted numbers, in the room, right now, and Endowment's two groups were both being asked to picture a counterfactual, nobody in either group was handed anything, and nobody's fingers ever touched a mug.

This matters because it isn't just a wording problem, one that a stronger imperative ("really imagine it") could fix. Kahneman, Knetsch and Thaler's own 1990 methodology used real mugs and a real, binding transaction specifically because the literature on hypothetical valuation shows imagined ownership does not reliably reproduce the same selling-price/buying-price gap that real, physical possession does. The paradigm's own original authors treated "really own it" as load-bearing to the effect, not incidental to it, so a version that drops the real object hasn't simplified the study, it has changed what's being measured.

**The check, going forward, before picking any future principle for this category.** Ask one question about the paradigm's own original methodology, not about the principle's plausibility in general: does the classic version of this study ask participants to judge a hypothetical vignette (a described scenario, a described price, a described choice), or does it depend on something real actually happening to the participant, a real object changing hands, a real delay before a real reward, a real stake being paid? If the founding study itself is a vignette design, a live phone-based version is faithful to it exactly as written, that's true of Framing (worded scenarios), Decoy and Compromise (described menus), and Perceived Fairness (described price rises), all four already live on this site and all four legitimate for the same reason: their own original papers asked people to judge a described situation, so asking a room to judge a described situation on a phone is the same paradigm, not a weakened stand-in for it. If the founding study specifically manipulates *real* possession, *real* delay, or *real* payment, because the effect is documented to weaken or vanish under a merely-imagined version, a live phone-only build can't replicate it faithfully, and the honest move is to pick a different principle, not to soften the language and hope the effect still shows up.

**The fix, in practice.** Endowment Effect's live tool was retired and replaced with Zero Price Effect (Shampanier, Mazar &amp; Ariely, 2007), whose own paradigm is a real-time choice between two real, priced chocolates, structurally identical to Framing/Decoy/Compromise/Fairness and requiring no physical prop or imagined state. The retired file (`endowment-live.html`, plus its two QR images) was deleted rather than left dangling, the `live-sessions.html` card and "All 7" anchor link were swapped from Endowment Effect to Zero Price Effect (same `pricing` category, so no count changes needed elsewhere), and this section was added so the next principle picked for this category gets checked against the real-versus-imagined test before any build work starts, not after an audience notices it doesn't work.

## A third interaction type: multi-select with a mean-count reveal, not just single-choice or a single number

**What happened.** The first seven tools all reduce to two shapes: `type: "choice"` (tap one of two options, reveal compares a % choosing the target) or `type: "number"` (submit one number, reveal compares a median). Diversification Heuristic doesn't fit either: the mechanism being demonstrated (Benartzi & Thaler's "1/n" naive diversification) is about how many options someone picks from a menu, not a single choice or a single freely-typed number. An options-review artifact proposed the real fix directly: each participant taps every fund on their group's real CommSec Pocket menu (group A: the real flat 10-option menu; group B: a curated 3-option redesign) that they'd personally invest in, and the reveal compares the average count picked per group, not a percentage or a median.

**The fix, in practice.** Added `type: "multiselect"` as a third CONFIG type, sharing the existing storage format with `"number"` (the logged value `v` is still a plain number, the count of checked boxes) so `addEntry`/`removeEntry`/history-table/session-log code needed zero changes. Three things did need real branches, not just a copy-paste of the `"number"` path:
- **The participant screen** is a genuinely different widget: a scrollable list of `<label class="multiselect-row"><input type="checkbox">...</label>` rows built straight from `CONFIG.groups[g].options` (the same option list the `"choice"` type already used, just multi-selectable instead of single-tap), plus a live "`N` selected" counter. On submit, the count of checked boxes becomes the logged value and the displayed confirmation ("Thanks, you picked: 4 funds.").
- **The reveal metric uses the mean, not the median.** A room's median count would round off exactly the kind of small differences (3.5 vs 1.5 funds) this demonstration exists to show; the artifact's own mockup explicitly called for "4.1 funds picked on average," so `groupMetric`/`fmtMetric` got a third branch (`isCount: true`) computing `mean()` (a new helper; only `median()` existed before) and formatting to one decimal place plus " funds", distinct from both the existing percentage and rounded-dollar/number formats.
- **The presenter's manual-tally input reuses the `"number"` type's UI**, not the `"choice"` type's per-option tap buttons, since a presenter typing in "4 funds, called out" is structurally identical to typing in "$40 sure" for a number-type tool. Extend the `CONFIG.type === 'number'` conditions that gate this UI to `CONFIG.type === 'number' || CONFIG.type === 'multiselect'` rather than duplicating the input-row markup under a new branch.

**The check, for the next new interaction type.** Before building a new `CONFIG.type` from scratch, check which existing type's *storage format* actually matches the new mechanism (a single logged number vs. a logged category key), and share that plumbing; then identify the two or three places that genuinely need new behaviour (usually: the participant-facing widget, the reveal's summary statistic, and whether the presenter's manual-entry UI can reuse an existing shape). Building a fourth type from scratch when it only actually differs from an existing one in the participant widget and the summary statistic duplicates a lot of code, other tool, for no real benefit.

## A fourth interaction type: the participant doesn't answer at all, the page runs the random process itself

**What happened.** The Sample Size Swing tool (built for the coin-flip special report, `the-coin-has-no-memory.html`) needed a participant to submit "the percentage of heads from 10 real coin flips" or "from 100 real coin flips." Nobody was going to physically flip 10 or 100 coins by hand at a live talk. The random process had to happen on the device itself, with the participant only choosing when to trigger it. None of the first three types fit: `"choice"` and `"multiselect"` assume a person is picking from options that already exist, and `"number"` assumes a person already knows the number they're submitting.

**The fix, in practice.** Added `type: "autoflip"` as a fourth CONFIG type, sharing the exact storage format with `"number"` (the logged value `v` is a plain percentage) so `addEntry`/`removeEntry`/`groupMetric`/`fmtMetric`/history-table code needed only a one-line `||` extension to their existing `CONFIG.type === 'number'` checks, not new branches. What's genuinely new:
- **The participant screen has no input at all**, just a single "Flip N coins" button. On tap it calls the shared `coin-engine.js` module's `CoinEngine.flipSequence(n)` and `CoinEngine.countHeads()`, computes the percentage, shows it briefly ("14 heads out of 20 (70%)"), then auto-submits, the same `renderThanks()` every other type uses. There is nothing to validate or disable/enable, because there is nothing to type.
- **The presenter's manual-tally UI is neither the `"number"` type's typed input nor the `"choice"` type's tap buttons**, because a presenter standing in for someone without their own phone shouldn't type in a called-out percentage (that invites transcription error on a number nobody can double-check by eye) or tap a category (there isn't one). It gets its own small branch: a single "Flip N on their behalf" button that runs the identical `CoinEngine` call the participant screen uses and logs the result directly, so the same fair, real random process backs every entry, self-served or presenter-triggered.
- **The reveal's summary statistic needed a genuinely new question**, not just a different formula on the same question. The other types ask "which group's typical answer was higher/more the target," a question this tool's own two groups can't answer meaningfully, since both are flipping the same fair coin and both should center near the same value. The demonstration is about *spread*, not center, so the reveal's narrative block compares each group's distance from the known true value (`|median − 50|`) instead of comparing the two medians to each other, and the scoreboard adds a `min`/`max` range line neither `"choice"` nor `"number"` needed.

**The check, extended.** The multiselect check above (share the closest type's storage format, then isolate the 2-3 genuinely new pieces) still holds, but this case adds a fourth question worth asking before building any future type: **is the room's answer actually a person's judgment, or is it the output of a process the device could run itself?** When a "measurement" is really a coin flip, a dice roll, or any other real random process with a known ground truth, the participant screen collapses to "trigger it" rather than "answer it," and the reveal's real question becomes how far the room's results sit from that known truth, not which group answered "more."

Each tool's own `CONFIG.mechanismHtml` (or, for `anchoring-live.html`, its hardcoded mechanism paragraph, the one tool old enough to predate the `CONFIG`-driven template) also picked up 1-2 bolded phrases on its own specific mechanism clause, and the two longest ones (`framing-live.html` at 129 words, `decoy-live.html` at 122) split into two paragraphs the same way. General lesson for the next skill written for a new content type: **before treating a formatting or writing rule as scoped to the skill that happens to name it, check whether the same visual shape (dense, unbroken, mobile-width prose) appears anywhere this skill's own output lands, and pull the rule forward rather than waiting for it to get flagged twice.**

## The 2026-09-01 catch: the QR/link block assumed the reader already knew what it was for

**What happened.** Every tool's reveal screen showed two QR cards with a bare group label ("Went in confident" / "Went in doubtful") and the raw URL printed as plain, non-tappable text underneath, wrapping mid-word across 3-4 lines on a real phone. Nothing on the screen itself said what a presenter is meant to do with these two codes, that mechanic only lived in the separate "How this runs at a live talk" list on `live-sessions.html`, a different page. The owner's catch, on a live screenshot of exactly this block: "This makes no sense. Need to be self explanatory and simple in all instructions and content and explanation after. Two distinct defects compounded here: (1) the block assumed the reader had already read a separate page's instructions, and (2) the URL text was decorative, not usable, unselectable in practice on a real phone and impossible to tap or cleanly copy.

Write the explaining sentence at the same time as the control, not after the first person who wasn't in the room while it was built points out that they can't tell what it does.

## The 2026-09-01 catch: design-conversation shorthand shipped as participant-facing copy

**What happened.** `biased-assimilation-live.html`'s excuse-picking screen asked participants "If someone pushed back on your rating, which explanation would you reach for?" with options like "A subset moved even if the headline number didn't" and "There's a backfire we haven't seen yet." The owner's catch, on a live screenshot of exactly this screen: "This for example is hard to understand. What does push back mean to a real user? The question not answers don't make sense. Needs to be easier and clearer to a normal person." He was right, and the root cause was traceable: "push back," "subset moved," and "backfire" were his own words, from his original dictated description of the concept earlier in this same session ("...explaining that while the overall metric didn't move as hoped there were subsets that may have... maybe there was a backfire with existing customers"). That framing was written for me, to design the mechanic correctly, and I carried it straight into the actual participant-facing button copy without ever translating it for the person who'd encounter it cold, a stranger scanning a QR code at a live talk with zero context about subsets, headline numbers, or business backfires.

**The root cause.** Language that's perfectly clear between two people mid-design-conversation, because both already share the concept it's shorthand for, is not automatically clear to a reader meeting it for the first time with no shared context. This is the live-tool-copy version of the standing global policy against review scaffolding leaking into a finished deliverable, the audience for the scaffolding (a designer, an editor, in this case the two of us working out the mechanic) is never the audience for the shipped thing.

**The check.** Before finalizing any participant-facing question or option text, ask: would this exact wording make sense to someone who has never been part of the conversation that produced it, using only words a random stranger uses in ordinary speech? Business/analytics register, "subset," "headline number," "metric," "pushed back," "backfire" used as a noun, is a specific tell to watch for, since it's exactly the vocabulary a design conversation about the mechanic naturally reaches for and exactly the vocabulary a live-talk participant never uses.

**The fix, in practice.** Rewrote the question as "Imagine someone says your rating is wrong. What would you tell them?" and all four excuse options into plain, sayable sentences: "Something outside the change was actually responsible," "It worked for some people, even though the overall number didn't move," "It helped, just not in the way we were measuring," "It might be quietly causing a problem we haven't noticed yet." Because the four options live in one shared `CONFIG.excuses` array feeding the participant buttons, the presenter's tally buttons, and the reveal screen's cross-tab bars all at once, fixing the array's `label`/`short` fields cascaded the plain language to every surface automatically, only the standalone prose on `live-sessions.html` (which restates the same four options as freestanding marketing copy) needed a separate, matching edit.

## The 2026-09-01 "for all" pass: auditing every tool for the same class of defect, not just the one flagged

**What happened.** Asked to check "all" tools after the excuse-picking screen's jargon was caught, a full read of every tool's participant-facing text (scenario titles, scenario bodies, and every option label, across all eleven tools) found eight already clean, plain, and jargon-free (concrete real-world objects: cameras, coins, snacks, chocolate, magazine subscriptions), and one more real defect of a *different kind* in `diversification-live.html`: the curated 3-option menu's third row, "See all 10 individually," reads as an action ("see all 10") but functions as an ordinary checkbox exactly like the two real fund options beside it, tapping it does nothing except register as a selected item. A participant reading it would reasonably expect a tap to reveal something. This isn't jargon, the words are all plain English, but it fails the identical underlying test: does the text mean, to a first-time reader with no design context, what it actually does?

**The check, generalized.** "Would a stranger reading this cold understand it" covers more than vocabulary. Two distinct sub-checks, both worth running on every option label and control on a reveal or participant screen: (1) **Is every word one an ordinary person would use in speech**, the jargon check from the excuse-picking catch. (2) **Does the label's own wording match what tapping it actually does**, checked separately, since a label can be perfectly plain English and still misdescribe its own behavior. A button, link, or checkbox whose label implies navigation, a reveal, or some other action needs to actually do that action, or it needs rewriting into an honest description of what selecting it actually means.

**The fix, in practice.** Reworded "See all 10 individually" to "None of these, I'd rather see all 10 first", a real, honest answer choice (recording a genuine reaction: this menu felt too limited) rather than a fake action masquerading as a checkbox, with a matching short label ("Wanted to see all 10") for the presenter tally button and history table. This is a wording fix only, distinct from the separate, still-open question of whether this tool's underlying metric (raw count of items tapped, capped differently at 10 vs. 3) is itself a fair comparison, that critique and its three proposed alternatives stand as their own unresolved item, not settled by this pass.

**Standing practice going forward.** When asked to fix something "for all" after one instance is caught, don't assume the same fix (a wording swap) generalizes to a search for the same words elsewhere. Re-run the actual underlying test, jargon-check and behavior-match-check both, against every tool's real content, since the same root failure ("built for someone who already understands the mechanic, not for the person meeting it cold") can surface as either wording or a mismatched affordance depending on the tool.

**What happened.** The excuse-picking question in `biased-assimilation-live.html` asked "Imagine someone says your rating is wrong. What would you tell them?" The owner's catch: "the issue I think is the ambiguity of 'wrong'. Its hard to interpret." He also flagged the scenario metric names themselves, e.g. "Application conversion rate," as too generic, asking for the specific thing being measured (his example: "is it start to submit application conversion or something else"). ## The 2026-09-01 catch, a second pass: a "wrong" fix that removed the ambiguous word but not the actual logic gap

**What happened.** The previous catch (above) fixed the excuse-picking question's wording, from "Imagine someone says your rating is wrong" to "...saw the exact same {metric} number and thinks your rating is off," on the theory that grounding the vague "wrong" in the participant's own number and the specific metric would resolve the ambiguity. It didn't fully land. The owner's next catch: "This is confusing because in the example the number went up... so it doesn't make sense in this content... to ask the question... it would make more sense for someone to say 'that may have appeared to work but...' or 'how do you know?'" The deeper problem the first fix missed: every scenario in this tool always shows a number moving in the direction that looks like the change worked (4.2% to 4.3%, 82.1% to 84.6%, and so on, that's the whole point of the exercise). A generic "thinks your rating is off" doesn't say *which way* it's off, too high or too low, and doesn't fit the one thing that's actually true about every scenario: the number moved in a direction that looks positive. Swapping one vague word for another slightly-less-vague phrase treated the symptom, not the underlying gap between the question's wording and the concrete content it sits on top of.

**The check, sharpened.** Fixing an ambiguous or confusing line isn't finished once the specific flagged word is gone. Re-read the new wording against the actual concrete content it references (here: a number that always improves), and ask whether the *logic* of the challenge still makes sense given what's literally shown on screen, not just whether the wording sounds more specific in isolation. A question can name a real number and a real metric and still not logically fit the scenario if it doesn't account for which direction that number moved.

**The fix, in practice.** The question became "You rated it {rating}/10. Someone in the room isn&rsquo;t convinced: &ldquo;That may look like it worked, but how do you know it wasn&rsquo;t something else?&rdquo; What would you tell them?", built directly from the owner's own suggested phrasing. Both readings make sense given the number always looks like an improvement, which the first attempted fix never actually addressed. ## Considered and rejected for the default: the Claude Artifact shared-state approach

Kept here because it's real, tested, working knowledge, useful if a future session explicitly wants live cross-device sync and explicitly accepts a claude.ai dependency to get it, not because it's the path to reach for by default.

The `artifact` capability's `publish(html)` call takes the **complete replacement document as a string**, and its own documentation warns against serializing the live DOM (`document.documentElement.outerHTML`) to build that string, since the live DOM can carry viewer-session state and runtime-injected scripts that don't belong in the next published version. The script that rebuilds the page has to describe the entire page, including itself, without literally containing a second, separately-maintained copy of its own source.

The stable solution, tested and working across multiple republish generations:

- Capture the script's own live text at the very top, synchronously, before any other script tag could run: `var OWN_SCRIPT_SRC = document.currentScript.textContent;`. Do the same for any `<style>` block that should carry forward unchanged.
- Write the document shell (doctype, head, body wrapper, the `<script>`/`<style>` tag markers) once, as a plain JS string constant, with placeholder tokens where the changing parts go. Escape every `</script` inside that string as `<' + '/script>` so the browser's original parser doesn't close the tag early.
- `buildHtml(state)` is `SHELL.replace(token, function(){ return value; })` per placeholder, using the function form of `.replace()` so a literal `$` in the script or data is never misread as a replacement pattern.
- `publish()` is compare-and-set: a `conflict` rejection means someone else published first, and the platform silently reloads every open view to the winner. Stash any pending write in `localStorage` before calling `publish()`, and on boot check whether it's missing from the freshly-loaded data before retrying, this is the documented, intended pattern, not a workaround. Bound the retries and fail honestly once they're exhausted.
- Treat a `not_writer` / `not_granted` / `capability_disabled` rejection, or `claude.use('artifact')` resolving `null`, as a permanent signal for that view: stop trying to write, and tell the participant their own answer plainly without claiming it joined a shared tally it didn't reach.
- **The real, never-resolved risk with this whole approach:** whether a stranger who only has a shared link gets write access at all, or loads read-only, was never confirmed in the pilot before the owner asked for the fully independent version instead. Treat this as a real open question requiring an actual test with a second, logged-out device, not an assumption, if this approach gets picked up again.
