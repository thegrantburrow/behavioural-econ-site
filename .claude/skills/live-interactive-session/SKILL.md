# Live Interactive Session

## Why this exists

Founded 2026-08-28 on a direct request: build a real, live, in-person demonstration of anchoring, two QR codes seeding two different anchors before the same estimate question, run with a real audience during a real talk, results shown live in the room. The owner's own framing: "New category of the website. These will be illustrative interactive sessions where an audience will experience behavioural science and economics in action." Anchoring was the pilot; more are expected to follow the same standard. This skill exists so the next one (loss aversion, social proof, whatever comes next) starts from the pipeline and the real technical lessons below, instead of re-deriving them.

**The pilot went through two real builds, not one, and the second is the one to copy.** The first build used a Claude Artifact's shared-state `publish()` capability to get a genuinely live, auto-updating results screen across every phone in the room. It worked (verified across multiple republish generations), but it meant participants landed on `claude.ai`, needed the artifact link to actually be shared with write access (an open question that was never confirmed), and depended on a platform outside this site entirely. When asked directly, the owner chose independence from Claude over the live auto-sync: "I need to be able to see them independent of Claude. Enable this." Faced with the explicit tradeoff (own site with no login prompt and no platform dependency, vs. live cross-device tally that only works on claude.ai), he picked the former. **Default to the static, no-backend build below for the next session in this category, and only reach for the Claude Artifact approach (kept further down for reference) if a future request explicitly asks for live cross-device sync and explicitly accepts the claude.ai dependency that comes with it.**

## What this content type is, and isn't

It's a **live, in-person replication of a real published paradigm**, run with an actual audience, not a read-only page and not a hypothetical. It's distinct from every other content type on this site: `behavioural-principle-article` explains a mechanism from its cited study; `experiment-blueprint` is a testable design nobody has run yet; `field-session` is a first-person recap of a talk after it happened. A Live Session is a tool people actually use, during the talk, and the "content" (the write-up, the citation, the framing) exists to support that live moment, not to stand alone. It shares one discipline with every other content type on the site: the paradigm has to be a real one from the literature, not an invented "fun fact" quiz.

## The pipeline, in order

1. **Pick a principle already on the site with a real, replicable lab paradigm**, not just a mechanism that's true in general. Anchoring works because Tversky & Kahneman (1974) is a clean two-step design (comparative judgment against a planted anchor, then a free estimate) that transfers directly to a phone screen. Not every principle transfers this cleanly, check whether the actual published methodology is something a room full of people can do in under a minute before committing to it.
2. **Design the paradigm faithfully**, not just "in the spirit of" the study:
   - A comparative judgment against the anchor ("more or less than X?") always comes before the free estimate, this is the real two-step design from Jacowitz & Kahneman (1995) and the original 1974 study, not a detail to drop for simplicity.
   - Use the real historical anchor values when the study you're replicating had specific ones (10 and 65 for the UN-Africa question), don't invent round numbers that feel plausible.
   - Assignment to condition has to be effectively blind and effectively random from the participant's side. Two QR codes that look identical (same design, same size, no visible label reading "A" or "B") satisfy this even though the underlying links differ, what matters is nothing on the page or in the room ever tells a participant which condition they're in.
   - Report the group gap as a **median**, not a mean, these estimate distributions are typically right-skewed and a mean gets pulled by outliers.
3. **Build it as a plain page on the site itself** (see "The default build" below), not a Claude Artifact, unless live cross-device sync has been explicitly requested and the claude.ai dependency explicitly accepted.
4. **Generate real QR codes pointing at the deployed page's URL**, one per condition, plus one for the presenter's tally/reveal view, using the site's own domain. Verify each one actually decodes to the intended URL with a real decoder before treating it as done, a QR code that looks right and doesn't scan right is worse than no QR code. Regenerate and re-verify them any time the hosting decision changes, a QR made for one URL is dead weight once the tool moves.
5. **Wire it into `live-sessions.html`** (or whichever page holds this category): the paradigm explained in plain language, real "try it yourself" links for someone browsing the site outside a live event, a cross-link to the full principle article for the citation and methodology critique, and a plain, honest explanation of how the room's results actually get compared (see below, this isn't automatic in the default build). Add the nav entry, footer link, sitemap entry, and homepage `explore-hub-card` the same way every other new category on this site gets wired in, that's not optional polish, it's how the category is actually reachable.

## The default build: fully static, no backend, persisted per device via localStorage

`grantburrow.com` has no backend and no database. The honest, fully-independent version of a "live" session accepts that a phone's individual answer has no way to travel to another phone or to a projector screen on its own, and designs around that instead of fighting it. It went through one real revision here too: the first pass kept the tally in a plain JS variable that vanished on reload, which surfaced two real gaps the moment the owner actually used it (see "Two real gaps found by actual use" below). The fix, now the default, uses `localStorage` as a genuine append-only log, not just an in-memory array:

- **The participant page** (`anchoring-live.html` for the pilot) is one plain HTML file, no external dependencies, reading which condition to show from a URL hash (`#g=a` / `#g=b`, never a query string, since a hash is guaranteed to work identically regardless of how the link reaches the browser and is never sent to any server). It runs the comparative question, then the estimate, then a thank-you screen. On submit, the answer is appended to the same `localStorage` log the results screen reads (see below), so if the participant and the results screen happen to share a browser (the owner's own testing, a shared kiosk device), it shows up automatically with no extra step. The thank-you screen still tells the participant plainly what to do for the real multi-phone case: **call out your number, or put your hand up, when the room compares notes**, since separate physical phones can never share `localStorage` with each other, only a shared backend could do that, and this build deliberately doesn't have one.
- **The log is a single append-only array in `localStorage`** (`{id, g, v, t, sessionId}` per entry), plus a small pointer to the *current session* (`{id, startedAt}`). Every entry, whether it arrived from a participant's own submission or the presenter typing in a called-out number, goes through the same `addEntry(group, value)` function into the same log, so the live tally is genuinely just "every logged entry belonging to the current session," not two separate code paths that can drift apart.
- **"Start new session" advances the session pointer, it never deletes anything.** The live tally and chart are filtered to the current session's id, so clicking it makes the numbers on screen go back to zero, but every prior session's entries stay in the log, groupable and viewable in a history table (date, time, group, per-entry value, an individual delete button). This is what actually satisfies "reset results for a new talk" and "keep a dated log" as the same feature instead of two competing ones.
- **A separate, more serious "clear all history" control** wipes the entire log and starts a fresh session, confirmed with the real entry count in the prompt ("permanently delete all 47 recorded answers"). Keep this visually and functionally distinct from "start new session", one is routine (used before every talk), the other is destructive and rare.
- Show the real fact's true answer as a marked reference line on the chart, and where the paradigm you're replicating has real published numbers (Tversky & Kahneman's own 45%/25% medians), show those too, clearly labelled as the original study's result, not this room's.

This gets you a real, live-feeling results reveal (the presenter types or a same-device phone submits, the bar chart moves, right there on the projector), a genuine dated record across many separate talks, and a real reset, all without a login, a platform dependency, or a backend.

## Two real gaps found by actual use, not by re-reading the spec

The first `localStorage`-free version of this build was reviewed, tested with Playwright, and shipped looking complete. It wasn't. The owner actually used it (entered one estimate on the Group A link, one on Group B) and reported: "Results didn't come. Nor did a QR code come up." Two separate, real gaps, neither of which a code review would have caught because the code did exactly what it was written to do, it just wasn't written to do enough:

1. **An in-memory-only tally can't show a participant's answer on any other screen, not even the same device's own results tab, because a fresh page load starts a brand new, empty JS variable.** The fix (this skill's default now) is to back the tally with `localStorage`, which persists across page loads and, load-bearing, is shared across every tab of the same browser on the same device. Test this for real the way the gap was actually found: submit an answer in one tab, open the results view in a second tab of the *same browser context*, confirm it appears, don't just trust that "no backend" was correctly implemented as "no persistence at all."
2. **Sending QR code images to the owner once, in chat, is not the same as the tool being able to produce them.** "Generate QR code for each when I start a session" was a real, reasonable ask: the results screen itself should show the codes, every time it's opened, not require a separate message asking for them again. Since the two participant URLs (`#g=a`, `#g=b`) never change between sessions, this doesn't need live QR generation, pre-render the two PNGs once (Python's `qrcode` library, verified against a real decoder, same as the printable copies), save them into `mockup/images/`, and have the results screen `<img>` them inline. Client-side JS QR generation was considered and rejected here specifically because this environment's CDN allowlist doesn't reliably reach arbitrary JS library hosts, a pre-rendered static image has no such dependency and is simpler besides.

## A real CSS trap: flex-centering a child that isn't a flex parent

The participant screens center content using `.screen { flex: 1; justify-content: center; }`. The first pass rendered pinned to the top instead. Root cause: `.screen`'s actual parent was a plain `<div id="app">` (re-rendered via `innerHTML`/`appendChild` on every screen change), and `#app` itself was NOT `display: flex`, so `.screen`'s own `flex: 1` had nothing to size against. The fix is one line, `#app { display: flex; flex-direction: column; flex: 1; min-height: 0; }`, but it's the kind of bug that looks fine in the markup and only shows up on an actual screenshot. Screenshot every screen at a real mobile width before calling a live-session tool built, don't just read the CSS and assume it centers.

## Don't rely on a platform's own share dialog to hand out per-view links

A real point of confusion in this pilot: the owner opened the artifact's own "Share" menu (Rename / Duplicate / Share / Version history, standard claude.ai chrome) expecting it to hand him a QR code for the specific view he wanted (Group A, Group B, or the reveal screen). A platform share dialog shares the canonical resource, it has no reason to know about a URL fragment like `#g=a` that only your own page's JavaScript understands. **Always generate and verify your own QR codes and plain-text links for each specific view your tool defines**, pointing at the exact full URL including whatever hash or parameter selects that view, and never assume a generic "Share" button will do this for you.

## The reveal screen needs a self-contained narrative, not just a chart

**What happened.** The Anchoring pilot's reveal screen shipped with a bar chart and a static historical-comparison line, but nothing telling the presenter (or anyone who screenshots the page later) what their specific numbers meant, whether this room's result actually replicated the classic effect, what the mechanism actually is, or where it shows up outside the room. The owner's request, verbatim: "This page below the answers should have a full narrative write up... using the results shown. Aka if they align to the anchoring and if they don't... mitigates by using as an interactive lesson eg sometimes noise in context can influence replication etc." A chart alone makes the reader do all the interpretation themselves; a live tool that already has the real numbers in hand should do that interpretation for them, every time it re-renders.

**The fix, in practice.** A `renderNarrative()` block, computed fresh on every render from the actual `byGroup` data (so it updates live as answers are added or removed), with three parts:
1. **A verdict that branches on the actual comparison**, not a fixed message: no data yet, one side still empty, medians tied, the classic direction (high anchor's median above low anchor's), or the reversed direction. Each branch is written for what it is, not as a generic "results may vary" hedge. The reversed branch is the one that matters most: it explicitly reassures that a single small room reversing the effect doesn't undo a well-replicated finding, names the real reason (noise, small per-group samples), and turns it into the stated lesson, that a single small study or session should never settle a question the way a large replication does, cross-linking to this site's own `small-sample-big-claim.html` report rather than just asserting it. A small-n caveat is added even to the aligned branch, so a real replication in a small room doesn't get oversold as more conclusive than it is.
2. **A self-contained mechanism paragraph**, written so a reader who lands on this exact page with zero other context (no principles.html visit, no session introduction) still gets the real explanation, matching the language already established on `principles.html#anchoring` (the anchoring-and-adjustment heuristic, adjustment stopping too early), with a link onward for the full write-up rather than duplicating it at length.
3. **Real, cited, relatable examples of the mechanism outside the room.** Five, each independently WebSearch-verified before writing (author, year, journal): credit card minimum repayments (Stewart, 2009), real estate listing-price anchoring on professional appraisers (Northcraft & Neale, 1987), first-offer advantage in negotiation (Galinsky & Mussweiler, 2001), judges' sentencing decisions anchored by a die roll (Englich, Mussweiler & Strack, 2006), and social-security-digit anchoring on auction bids (Ariely, Loewenstein & Prelec, 2003). Picking examples that are genuinely anchoring, not an adjacent mechanism (decoy pricing, framing, scarcity) that merely feels related, matters as much here as it does in `science-behind-article`'s own mismatched-mechanism failure mode.

**The check.** Verify every branch actually renders, not just the happy path: seed `localStorage` directly (via Playwright's `page.evaluate`, then `page.reload()`, not `page.goto()` again, since a second `goto` can race the reload before the seeded data is read) with empty, one-sided, aligned, tied, and reversed data, and screenshot each. A tool whose whole point is showing real-time results needs its interpretation layer tested across the actual range of results it can produce, not just the one the developer happened to type in first.

## The reveal screen is projected on a wall, design for that distance, not for a phone

**What happened.** The pilot's reveal screen (and the 5 tools that copied its structure) used the same type scale as the participant screens, 12-16px body text, a 26px-tall bar chart, a 28px median number, because nothing distinguished "a screen someone reads up close" from "a screen a room reads from the back row." The owner's catch, verbatim, pointing at the live URL: "Results page should be Much More visually engaging with example and visualisation like we've built imagine on a large screen with a room." A page sized for a phone doesn't scale up into a good projector screen just because a browser can zoom, the whole information hierarchy needs to change: one or two numbers matter at a glance, everything else is secondary.

**The fix, in practice.** The reveal screen is really two audiences sharing one URL, and the layout has to say so:

1. **A room-scale scoreboard is the single focal point**, not a chart among several. Two big cards, one per group, each showing that group's headline number at `clamp(52px,8.5vw,104px)`, Georgia, bold, big enough to read from the back of a room, with a small circular "VS" badge between them and an animated fill bar underneath (`width:0` at creation, set to the real percentage inside a `requestAnimationFrame` callback so the transition actually plays instead of snapping straight to its final state). A `scPop` keyframe (`scale(.7)&rarr;scale(1.07)&rarr;scale(1)`) on the number itself gives every re-render, a new answer coming in live, a visible "pop" rather than a silent DOM swap. A `.scoreboard-gap` line underneath states the actual gap in plain language ("40 percentage points apart between the two groups, same real question, same room"), doing the subtraction for the room instead of making people eyeball two bars.
2. **Presenter input controls get visually demoted, on purpose**, into a `.presenter-controls` box: dashed border, muted background, small type, an explicit "Presenter controls" eyebrow and a one-line note ("This box is for whoever is running the session, not for the projector"). The same input fields and choice buttons from before still work exactly the same, they just no longer compete with the big numbers for attention. Don't duplicate the big median/percentage inside this box too, once it's shown large in the scoreboard, repeating it here in small type is redundant, not reassuring.
3. **A historical comparison with real structured numbers** (a study's own high/low or A/B medians, not just a citation sentence) can become a second, smaller two-column mini-scoreboard in the same visual language, exactly like Anchoring's "This room vs. the original 1974 study" grid. A tool whose citation is prose-only (no clean paired numbers to chart, most of the 5 non-Anchoring tools) doesn't get a fabricated chart to force the parallel, it gets a plainly labelled `.historical-card` callout instead, bigger and better-framed than a bare paragraph, but honest about not having comparable structured data to plot.
4. **QR codes get bigger too** (`max-width:260px`, up from 200px), since a phone in the back of a real room has to resolve a projected code from several metres away, not just look tidy in a browser tab.

**The check.** Screenshot the scoreboard specifically (not just the full page) at a real large-display width (1600&times;1000 or wider, simulating a projector or a big screen, not just a phone), for the empty state, the aligned state, and the reversed state, and confirm the big numbers, the VS badge, and the gap line all read clearly at that scale before calling a redesign done. Re-check the participant screens and the full mobile reveal layout too, a redesign aimed at a room-scale audience has broken the phone-scale audience before if it isn't checked both ways.

## Voice and rigor, same as everywhere else on the site

- **No em dashes**, anywhere a participant or reader sees text: the tool's own copy, the site page, the QR labels.
- **Never fabricate the real-world answer, or a historical study's real numbers.** Verify the fact's true value (the UN-Africa percentage, or whatever the next session's fact is) the same way any other citation on this site gets verified, and if you show a founding study's own result for comparison, cite it accurately rather than rounding it into something tidier.
- **State trade-offs plainly, don't silently pick one and hope nobody asks.** "No live cross-device tally" is a real, stated limitation of the default build, not something to gloss over in the page copy. The one time this pilot didn't do that (assuming a claude.ai share link would grant write access to strangers) is exactly why the whole approach got rebuilt.

## Considered and rejected for the default: the Claude Artifact shared-state approach

Kept here because it's real, tested, working knowledge, useful if a future session explicitly wants live cross-device sync and explicitly accepts a claude.ai dependency to get it, not because it's the path to reach for by default.

The `artifact` capability's `publish(html)` call takes the **complete replacement document as a string**, and its own documentation warns against serializing the live DOM (`document.documentElement.outerHTML`) to build that string, since the live DOM can carry viewer-session state and runtime-injected scripts that don't belong in the next published version. The script that rebuilds the page has to describe the entire page, including itself, without literally containing a second, separately-maintained copy of its own source.

The stable solution, tested and working across multiple republish generations:

- Capture the script's own live text at the very top, synchronously, before any other script tag could run: `var OWN_SCRIPT_SRC = document.currentScript.textContent;`. Do the same for any `<style>` block that should carry forward unchanged.
- Write the document shell (doctype, head, body wrapper, the `<script>`/`<style>` tag markers) once, as a plain JS string constant, with placeholder tokens where the changing parts go. Escape every `</script` inside that string as `<' + '/script>` so the browser's original parser doesn't close the tag early.
- `buildHtml(state)` is `SHELL.replace(token, function(){ return value; })` per placeholder, using the function form of `.replace()` so a literal `$` in the script or data is never misread as a replacement pattern.
- `publish()` is compare-and-set: a `conflict` rejection means someone else published first, and the platform silently reloads every open view to the winner. Stash any pending write in `localStorage` before calling `publish()`, and on boot check whether it's missing from the freshly-loaded data before retrying, this is the documented, intended pattern, not a workaround. Bound the retries and fail honestly once they're exhausted.
- Treat a `not_writer` / `not_granted` / `capability_disabled` rejection, or `claude.use('artifact')` resolving `null`, as a permanent signal for that view: stop trying to write, and tell the participant their own answer plainly without claiming it joined a shared tally it didn't reach.
- **The real, never-resolved risk with this whole approach:** whether a stranger who only has a shared link gets write access at all, or loads read-only, was never confirmed in the pilot before the owner asked for the fully independent version instead. Treat this as a real open question requiring an actual test with a second, logged-out device, not an assumption, if this approach gets picked up again.
