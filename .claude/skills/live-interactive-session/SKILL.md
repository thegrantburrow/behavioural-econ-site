# Live Interactive Session

## Why this exists

Founded 2026-08-28 on a direct request: build a real, live, in-person demonstration of anchoring, two QR codes seeding two different anchors before the same estimate question, run with a real audience during a real talk, results shown live in the room. The owner's own framing: "New category of the website. These will be illustrative interactive sessions where an audience will experience behavioural science and economics in action." Anchoring was the pilot; more are expected to follow the same standard. This skill exists so the next one (loss aversion, social proof, whatever comes next) starts from the pipeline and the real technical lessons below, instead of re-deriving them.

**The pilot went through two real builds, not one, and the second is the one to copy.** The first build used a Claude Artifact's shared-state `publish()` capability to get a genuinely live, auto-updating results screen across every phone in the room. It worked (verified across multiple republish generations), but it meant participants landed on `claude.ai`, needed the artifact link to actually be shared with write access (an open question that was never confirmed), and depended on a platform outside this site entirely. When asked directly, the owner chose independence from Claude over the live auto-sync: "I need to be able to see them independent of Claude. Enable this." Faced with the explicit tradeoff (own site with no login prompt and no platform dependency, vs. live cross-device tally that only works on claude.ai), he picked the former. **Default to the static, no-backend build below for the next session in this category, and only reach for the Claude Artifact approach (kept further down for reference) if a future request explicitly asks for live cross-device sync and explicitly accepts the claude.ai dependency that comes with it.**

## What this content type is, and isn't

It's a **live, in-person replication of a real published paradigm**, run with an actual audience, not a read-only page and not a hypothetical. It's distinct from every other content type on this site: `behavioural-principle-article` explains a mechanism from its cited study; `experiment-blueprint` is a testable design nobody has run yet; `field-session` is a first-person recap of a talk after it happened. A Live Session is a tool people actually use, during the talk, and the "content" (the write-up, the citation, the framing) exists to support that live moment, not to stand alone. It shares one discipline with every other content type on the site: the paradigm has to be a real one from the literature, not an invented "fun fact" quiz.

## The pipeline, in order

1. **Pick a principle already on the site with a real, replicable lab paradigm**, not just a mechanism that's true in general. Anchoring works because Tversky & Kahneman (1974) is a clean two-step design (comparative judgment against a planted anchor, then a free estimate) that transfers directly to a phone screen. Not every principle transfers this cleanly, check whether the actual published methodology is something a room full of people can do in under a minute before committing to it.
2. **Design the paradigm faithfully**, not just "in the spirit of" the study:
   - A comparative judgment against the anchor ("more or less than X?") always comes before the free estimate, this is the real two-step design from Jacowitz & Kahneman (1995) and the original 1974 study, not a detail to drop for simplicity.
   - Use the real historical anchor values when the study you're replicating had specific ones (10 and 65 for the UN-Africa question), don't invent round numbers that feel plausible.
   - Assignment to condition has to be effectively blind and effectively random from the participant's side. Two QR codes that look identical (same design, same size, no visible label reading "A" or "B") satisfy this even though the underlying links differ, what matters is nothing on the page or in the room ever tells a participant which condition they're in.
   - Report the group gap as a **median**, not a mean, these estimate distributions are typically right-skewed and a mean gets pulled by outliers.
3. **Build it as a plain page on the site itself** (see "The default build" below), not a Claude Artifact, unless live cross-device sync has been explicitly requested and the claude.ai dependency explicitly accepted.
4. **Generate real QR codes pointing at the deployed page's URL**, one per condition, plus one for the presenter's tally/reveal view, using the site's own domain. Verify each one actually decodes to the intended URL with a real decoder before treating it as done, a QR code that looks right and doesn't scan right is worse than no QR code. Regenerate and re-verify them any time the hosting decision changes, a QR made for one URL is dead weight once the tool moves.
5. **Wire it into `live-sessions.html`** (or whichever page holds this category): the paradigm explained in plain language, real "try it yourself" links for someone browsing the site outside a live event, a cross-link to the full principle article for the citation and methodology critique, and a plain, honest explanation of how the room's results actually get compared (see below, this isn't automatic in the default build). Add the nav entry, footer link, sitemap entry, and homepage `explore-hub-card` the same way every other new category on this site gets wired in, that's not optional polish, it's how the category is actually reachable.

## The default build: fully static, no backend, presenter-run tally

`grantburrow.com` has no backend and no database. The honest, fully-independent version of a "live" session accepts that a phone's individual answer has no way to travel to another phone or to a projector screen on its own, and designs around that instead of fighting it:

- **The participant page** (`anchoring-live.html` for the pilot) is one plain HTML file, no external dependencies, reading which condition to show from a URL hash (`#g=a` / `#g=b`, never a query string, since a hash is guaranteed to work identically regardless of how the link reaches the browser and is never sent to any server). It runs the comparative question, then the estimate, then a thank-you screen that tells the participant plainly what happens next: **call out your number, or put your hand up, when the room compares notes.** This is not a lesser version of the demonstration, the actual anchoring effect happens the moment someone privately answers on their own phone; the aggregation step is bookkeeping, and it's fine for bookkeeping to be manual.
- **The presenter's tally screen** (`#reveal` on the same file) is a second small tool on the same page: a numeric input per condition, an "Add" button, a running median and a live bar chart, all recalculated in that browser tab's own memory as the presenter types in the numbers a show of hands or a handful of volunteers call out. Nothing is sent anywhere and nothing persists between page loads, which is the honest, stated trade-off for having zero backend. Show the real fact's true answer as a marked reference line on the chart, and where the paradigm you're replicating has real published numbers (Tversky & Kahneman's own 45%/25% medians), show those too, clearly labelled as the original study's result, not this room's.
- A "clear tally" control just resets the in-memory arrays for the next talk, no confirmation step needed beyond a plain `confirm()`, since nothing is actually being deleted from anywhere durable.

This gets you a real, live-feeling results reveal (the presenter types, the bar chart moves, right there on the projector) without a login, without a platform dependency, and without ever silently overselling what the tool can actually do.

## A real CSS trap: flex-centering a child that isn't a flex parent

The participant screens center content using `.screen { flex: 1; justify-content: center; }`. The first pass rendered pinned to the top instead. Root cause: `.screen`'s actual parent was a plain `<div id="app">` (re-rendered via `innerHTML`/`appendChild` on every screen change), and `#app` itself was NOT `display: flex`, so `.screen`'s own `flex: 1` had nothing to size against. The fix is one line, `#app { display: flex; flex-direction: column; flex: 1; min-height: 0; }`, but it's the kind of bug that looks fine in the markup and only shows up on an actual screenshot. Screenshot every screen at a real mobile width before calling a live-session tool built, don't just read the CSS and assume it centers.

## Don't rely on a platform's own share dialog to hand out per-view links

A real point of confusion in this pilot: the owner opened the artifact's own "Share" menu (Rename / Duplicate / Share / Version history, standard claude.ai chrome) expecting it to hand him a QR code for the specific view he wanted (Group A, Group B, or the reveal screen). A platform share dialog shares the canonical resource, it has no reason to know about a URL fragment like `#g=a` that only your own page's JavaScript understands. **Always generate and verify your own QR codes and plain-text links for each specific view your tool defines**, pointing at the exact full URL including whatever hash or parameter selects that view, and never assume a generic "Share" button will do this for you.

## Voice and rigor, same as everywhere else on the site

- **No em dashes**, anywhere a participant or reader sees text: the tool's own copy, the site page, the QR labels.
- **Never fabricate the real-world answer, or a historical study's real numbers.** Verify the fact's true value (the UN-Africa percentage, or whatever the next session's fact is) the same way any other citation on this site gets verified, and if you show a founding study's own result for comparison, cite it accurately rather than rounding it into something tidier.
- **State trade-offs plainly, don't silently pick one and hope nobody asks.** "No live cross-device tally" is a real, stated limitation of the default build, not something to gloss over in the page copy. The one time this pilot didn't do that (assuming a claude.ai share link would grant write access to strangers) is exactly why the whole approach got rebuilt.

## Considered and rejected for the default: the Claude Artifact shared-state approach

Kept here because it's real, tested, working knowledge, useful if a future session explicitly wants live cross-device sync and explicitly accepts a claude.ai dependency to get it, not because it's the path to reach for by default.

The `artifact` capability's `publish(html)` call takes the **complete replacement document as a string**, and its own documentation warns against serializing the live DOM (`document.documentElement.outerHTML`) to build that string, since the live DOM can carry viewer-session state and runtime-injected scripts that don't belong in the next published version. The script that rebuilds the page has to describe the entire page, including itself, without literally containing a second, separately-maintained copy of its own source.

The stable solution, tested and working across multiple republish generations:

- Capture the script's own live text at the very top, synchronously, before any other script tag could run: `var OWN_SCRIPT_SRC = document.currentScript.textContent;`. Do the same for any `<style>` block that should carry forward unchanged.
- Write the document shell (doctype, head, body wrapper, the `<script>`/`<style>` tag markers) once, as a plain JS string constant, with placeholder tokens where the changing parts go. Escape every `</script` inside that string as `<' + '/script>` so the browser's original parser doesn't close the tag early.
- `buildHtml(state)` is `SHELL.replace(token, function(){ return value; })` per placeholder, using the function form of `.replace()` so a literal `$` in the script or data is never misread as a replacement pattern.
- `publish()` is compare-and-set: a `conflict` rejection means someone else published first, and the platform silently reloads every open view to the winner. Stash any pending write in `localStorage` before calling `publish()`, and on boot check whether it's missing from the freshly-loaded data before retrying, this is the documented, intended pattern, not a workaround. Bound the retries and fail honestly once they're exhausted.
- Treat a `not_writer` / `not_granted` / `capability_disabled` rejection, or `claude.use('artifact')` resolving `null`, as a permanent signal for that view: stop trying to write, and tell the participant their own answer plainly without claiming it joined a shared tally it didn't reach.
- **The real, never-resolved risk with this whole approach:** whether a stranger who only has a shared link gets write access at all, or loads read-only, was never confirmed in the pilot before the owner asked for the fully independent version instead. Treat this as a real open question requiring an actual test with a second, logged-out device, not an assumption, if this approach gets picked up again.
