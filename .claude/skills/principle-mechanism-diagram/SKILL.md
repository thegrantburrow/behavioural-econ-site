# Principle Mechanism Diagram

## Which visual system this is

This skill governs exactly one of the site's icon/illustration systems:
the `.illustration` mechanism diagram built from `icons.py` (system #2 in
the repo's `VISUAL-SYSTEMS.md`). It is NOT the same system as the small
per-principle eyebrow tag icon (`.principle-icon`, system #1 in that same
file) that sits inline with the principle's heading, nor any of the other
dozen-plus icon systems catalogued there (case-card icons, flow-diagram
icons, app/doc mockup icons, and so on). If a request is actually about the
eyebrow tag icon, a different page's icon system, or something off-site
like a logo that should echo "the site's iconography" in general, stop and
check `VISUAL-SYSTEMS.md` for the right match before reaching for
`icons.py` — that mismatch has already happened once this session and
produced generic-clip-art results (a giant star, a giant checkmark) sized
for illustration scale, not eyebrow-tag scale.

## Why this exists

Every Principles article on Field Notes is built on a real, cited academic study — that's the site's whole credibility model (see `behavioural-principle-article` skill: citation, methodology critique, paraphrase-tagged excerpts, no invented data presented as real). A hand-drawn mechanism diagram filling an empty illustration slot inherits that same obligation: it isn't a free illustrative sketch, it's a claim about what a specific cited study found, rendered visually. Three ways that claim can go quietly wrong all happened in one review cycle on this site and had to be corrected:

1. **Source substitution** — drawing the site's own worked example (an experiment blueprint, a hypothetical scenario) instead of the principle's actual seminal cited paper.
2. **Generic-object drift** — drawing a plausible-sounding invented scenario instead of the literal real-world object or setting the cited study used.
3. **Unevidenced extension** — drawing a callout or arrow that implies a causal claim beyond what the article text or citation excerpts actually say.

A fourth, purely mechanical failure mode compounds all three: reviewing the result at thumbnail scale, where text-collision bugs are invisible.

## Failure mode 1: source substitution

**What happened.** The Halo Effect principle's seminal citation is Thorndike (1920) — real supervisors rating real subordinates on independent traits that correlated implausibly highly. The first diagram instead illustrated this site's own `digital-home-loan-halo` experiment blueprint (a bank launching a digital home loan channel) — a real, well-built piece of content, but not what the principle itself names as its evidence. The user's own catch: "rather than using my experiment I'd run … do diagram using the seminal academic paper and experiment."

**The check.** Before drawing anything, answer: what is the *first, primary* `study-card` citation inside this principle's `<details class="article">` block in `mockup/principles.html`? That is the seminal source. If the site's own experiments.html has a worked example built on the same principle, that's a legitimate *second* diagram for the experiment page itself — not a substitute for the principle's own illustration, which should ground itself in the principle's own cited evidence first.

**The fix, in practice.** Read the citation's `excerpts` block (the `paraphrase`-tagged findings) and build the diagram directly from those sentences — same named traits, same real numbers, same actual mechanism the study card describes. Don't invent a scenario that merely *resembles* the mechanism.

## Failure mode 2: generic-object drift

**What happened.** The Goal Gradient Effect's cited study (Kivetz, Urminsky & Zheng, 2006) is a real café field experiment: a 10-stamp coffee card vs. a 12-stamp card with 2 free coffees, both needing exactly 10 more purchases. The first diagram used generic circles labelled "stamps" on an unnamed loyalty card — accurate to the count in isolation, but abstracted away from the one detail (it's a *coffee* card) that makes the study recognisable and concrete. The user's own catch: "Need to be clearer that it's a coffee loyalty card." A related, sharper version of the same failure: that first diagram also got the count wrong (8 stamps, 2 pre-filled, i.e. unequal remaining distance) before being corrected to the study's real 12-vs-10 design — generic invented numbers are exactly as risky as a generic invented object.

**The check.** Before drawing, name the literal object, setting, and quantities the cited study used — not an analogous stand-in. If the study is a café loyalty card, draw a coffee cup, not a circle; if it's 12-vs-10 stamps, draw 12 and 10, not a rounder number that "feels" similar. Genericising a real study's concrete details doesn't make a diagram more broadly applicable — it just makes it unverifiable at a glance and, as happened here, easier to get quietly wrong.

**The fix, in practice.** Build a small reusable `<symbol>` for the literal object (a coffee-cup icon, defined once in `<defs>` and placed with `<use>`) rather than a generic circle/rect standing in for it. Label the artefact by its real name ("COFFEE CARD," not "LOYALTY CARD") in the diagram itself, not just the caption.

## Failure mode 3: unevidenced extension

**What happened.** For the Compromise Effect, the user asked for a "sister diagram" showing that adding a compromise option also lifts *total* sales, not just redistributes share among the tiers already offered. Checked against the actual cited study (Simonson, 1989, the real camera experiment: two cameras split 50/50; adding a third pushed the middle one to 57%) — that's share redistribution in a fixed, forced-choice set, not a measurement of total purchase vs. no-purchase. A targeted search for the adjacent claim (does a compromise option reduce choice deferral / lift total conversion) turned up marketing-blog assertions but no specific controlled study measuring compromise-present vs. compromise-absent against a real no-purchase outcome — and the one directly relevant academic paper on deferral (Dhar, 1997) found deferral is driven by how close the options' attractiveness is, not by tradeoff difficulty, which doesn't cleanly support the claim either.

**The check.** Before drawing any callout, arrow, or label that asserts a causal claim — especially a secondary or "obviously true" extension of the headline finding — find the literal sentence in the principle's own article text or citation excerpt that supports it. If you can't find one, a quick supporting search (WebSearch) is worth doing before concluding either way. If neither the site's own text nor a real search turns up a specific study measuring that exact claim, don't draw it as fact.

**The fix, in practice.** Report the gap directly instead of inventing a plausible-sounding diagram: what the cited study actually measured, what was checked for the extended claim, and what was found (or not found). Offer the options this site's own conventions already support — research it properly and add a real citation before drawing anything, draw it explicitly labelled as an untested hypothesis (mirroring the `experiment-blueprint` skill's "Illustrative, not real/disclosed data" convention), or drop it and keep the diagram scoped to what's actually evidenced. Let the user choose rather than guessing.

## Failure mode 4 (process): thumbnail-scale review hides real bugs

**What happened.** Two rounds of this diagram set shipped with real text-collision bugs (three tier labels overlapping in the Compromise diagram, a callout overlapping a card label in Goal Gradient) that were invisible in a full-page screenshot at ~340px display width, and only became obvious once a single `.mock-illustration` element was screenshotted in isolation at 2x device-scale.

**The check.** Before presenting any hand-coded SVG diagram, screenshot each `.mock-illustration` element individually (Playwright `element.screenshot()`, not `page.screenshot()`), at `device_scale_factor=2` or higher. A full-page shot is fine for checking overall flow; it is not sufficient for checking whether text inside a 400×300 viewBox actually fits.

## Failure mode 5 (process): decorative lines bleeding through caption text

**What happened.** Several diagrams in the batch that completed all 48 principles used a dashed vertical divider (or a horizontal saturation-scale arrow) running the full height of the 400×300 viewBox to separate a two-panel "before / after" or "condition A / condition B" layout. Because SVG draws in document order and text has no opaque background, a divider drawn *before* a caption placed later in the markup showed through the caption's letterforms wherever the line's x-position crossed the text — invisible at thumbnail scale, visible at 2x per-diagram screenshot (the same review step failure mode 4 mandates). Caught in: Shooting the Messenger, Chef or the Ingredients, Good Friction, Spillovers.

**The check.** Any decorative rule, divider, or arrow that spans most of the viewBox's height or width will cross any full-width caption placed below it. Before finalizing, check the y-range (or x-range) of every divider/rule against the y-position of every text element drawn after it.

**The fix, in practice.** Stop the divider short — end it above the first caption's baseline (e.g. `y2="165"` instead of `y2="230"` when captions start around `y="185"`) rather than running it the full box height. A partial divider that visually separates the two labelled panels above still reads correctly; it doesn't need to reach the bottom of the box.

## Failure mode 6: false precision on a reference point that isn't one of the compared options

**What happened.** The Loss Aversion diagram illustrated Tversky & Kahneman (1991)'s job-choice study: participants chose between a fixed Job X (isolated, 20-minute commute) and Job Y (social, 60-minute commute), and which one they preferred depended on which job they were told was their *current* one — a third, separate job, described only as "isolated with a 10-minute commute" or "social with an 80-minute commute," never identical to X or Y. The diagram labeled that reference job "CURRENT JOB: ISOLATED, 10-MIN" directly above a box reading "chooses Job X" (20-min) — real numbers, accurately transcribed from the study, but placed so that a reader expects the 10 to reappear in the choice and it doesn't. The user's own catch, verbatim: "This doesn't make sense... find alternate example or explain better." The diagram wasn't wrong on the facts; it was illegible because it implied a numeric match it never intended.

**The check.** Whenever a diagram includes a reference point, anchor, or "current state" that is described with a specific number but is *not itself one of the options being compared*, ask: will a reader expect that number to reappear somewhere else in the diagram? If yes — because it's sitting right next to a similar-looking number that's close but different — either the numbers need to actually match, or the reference needs to drop numeric precision entirely and state only the qualitative direction (a category, not a value) that the mechanism actually depends on.

**The fix, in practice.** Redrew the reference as a purely qualitative condition — "TOLD THEIR ROUTINE IS ISOLATED & QUIET" / "...SOCIAL & BUSY" — with no minute figure attached, sitting clearly above the fixed, once-stated Job X/Job Y options with their real 20-min/60-min numbers. Nothing invites a false comparison anymore because nothing that looks comparable is left unmatched. The general version of this rule: two numbers that are close but not equal, placed near each other in a diagram, read as an error unless the diagram explicitly marks them as unrelated — so either match them, separate them further, or drop the precision that isn't load-bearing for the point being made.

## Failure mode 7: terracotta or teal text/strokes on a mustard background fail contrast

**What happened.** The Signpost Effect diagram (`bg-mustard`) used terracotta (`#B2472B`) as the fill for a `<text>` label ("LABEL: 6/10 GAS RATING") and for an italic caption ("efficient car chosen more often"), directly on the mustard (`#D9A441`) background. Measured against the actual hex values, mustard's relative luminance is ≈0.417 and terracotta's is ≈0.142, giving a contrast ratio of **≈2.4:1** — well under the WCAG AA minimum of 4.5:1 for normal text (or even 3:1 for large text/graphical objects). Teal (`#2B6660`) on mustard measures similarly weak, ≈2.9:1. The user's catch, verbatim: "These colours are hard to read together." An audit of every other `bg-mustard` diagram on the site found the identical bug repeated 13 more times — bare terracotta text, thin strokes, card borders, and connector lines sitting directly on mustard, all in the same unreadable range.

**The check.** On any `bg-mustard` diagram, before finalizing, grep the SVG for `fill="#B2472B"` or `stroke="#B2472B"` (and the teal equivalents) on `<text>` elements or on unfilled `<line>`/`<path>`/`<circle>`/`<ellipse>`/`<rect>` elements (i.e. anything drawn as a thin stroke rather than a solid fill). Any match is a contrast failure waiting to be found by a reader, not a maybe.

**The fix, in practice.** The rule is about *fill vs. stroke*, not about banning the color: a **large solid-filled shape** in terracotta or teal (a filled circle, bar, card, chip) still reads fine on mustard, because shape and hue difference carry the recognition even at low luminance contrast — none of those needed to change. What must change is any **text, thin stroke, or unfilled outline** in terracotta/teal sitting directly on the mustard field: convert its color to ink (`#1E1B16`), and carry emphasis/hierarchy through font-weight, size, or opacity instead of hue. A filled terracotta shape with light text sitting *on top of* that shape is unaffected by this rule either, since that pairing (light text on a dark, saturated fill) has strong contrast on its own. Re-screenshot every diagram touched at 2x per the failure-mode-4 process before considering the fix done — several of the 13 fixes here revealed further stroke-only instances (a card border, a connector line, a small unfilled circle) that a first pass of text-only search missed, so check `<circle>`/`<ellipse>`/`<rect>` strokes explicitly, not just `<text>` and `<line>`.

**Grep gotcha found later (rollout batch 7, mental-accounting).** A pair of X-mark `<path>` elements (`M46 76 L100 106 M100 76 L46 106`, an open multi-subpath line with no real fillable area) used `stroke="#B2472B"` with **no `fill` attribute at all** — not `fill="none"`. An automated check that pattern-matches for `fill="none"` alongside the stroke color misses this: SVG's default fill is black, so the element has no explicit `fill="none"` to match, even though visually it is a pure terracotta stroke on mustard with the identical 2.4:1 contrast failure. Any contrast grep must flag `stroke="#B2472B"`/`stroke="#2B6660"` on a `<path>`, `<line>`, `<circle>`, `<ellipse>`, or `<rect>` regardless of whether `fill` is present, absent, or `"none"` — check the stroke color alone, not the fill/stroke pair.

## Failure mode 8: abstract charts that need the caption to make sense, instead of narrating themselves

**What happened.** A first redesign pass on three diagrams (Loss Aversion, Halo Effect, Goal Gradient) replaced text-box-heavy layouts with cleaner shapes: rating bars, generic job-card rectangles, an arrow pair labelled only "STEADY PACE" / "PACE PICKS UP." Visually tidier, but a reader landing on the diagram alone — no caption read yet, no mechanism-note read yet — couldn't tell *why* the pace changed or *what* the bars were comparing. The user's catch, verbatim: "the diagram isn't self contained and explanatory," and on the second attempt, "these looks the same" — meaning the structural problem (dependence on outside text to be legible) hadn't actually moved, only the shapes had.

**The check.** Cover the caption and the mechanism-note beneath the diagram, then look at the diagram alone: can a reader who has read nothing else state what happened, to whom, and why, just from what's drawn? If the answer relies on a label like "PACE PICKS UP" that names an *outcome* without naming the *cause* ("closer to the reward" — the actual mechanism), the diagram is illustrating a chart of the finding, not the finding's mechanism.

**The fix, in practice.** Borrow the icon-plus-concrete-label chain already established in `mockup/sessions.html` and `mockup/experiments.html`'s `.flow-diagram` component (a small stroke-icon directly paired with a short, specific text label, chained step-to-step with arrows) and adapt it inside the `viewBox="0 0 400 300"` illustration frame — a small icon plus a *specific, concrete* label at every node the diagram passes through, not just at the start and end. Two structural patterns cover most mechanisms and were used across the shipped redesign (`mockup/principles.html#loss-aversion`, `#halo-effect`, `#goal-gradient`, read as worked examples):
- **Linear chain** — a single sequence of causes, one leading to the next (Halo Effect: one trait noticed → one impression formed → two unrelated traits rated the same).
- **Parallel rows** — two versions of the same setup run side by side, each row a straight left-to-right chain on its own, so the one real difference between them is visually obvious without cross-referencing the other row (Loss Aversion: two identical "current routine → same two jobs → job kept" rows, one per starting condition; Goal Gradient: blank card → steady pace, pre-filled card → faster pace, both needing the identical 10 more purchases).
A third pattern, **fan converge/diverge** (multiple starting conditions funnelling into one shared middle node, then fanning back out to multiple outcomes via diagonal arrows), was tried for Loss Aversion in this same redesign and rejected — see failure mode 9. Don't reach for it; use two parallel rows instead, even though it means drawing the shared middle state twice.
Every node's label must name the *specific* thing happening there (what was said, what was seen, what was chosen), not a generic category — "TOLD THIS IS CURRENT" plus "quiet, short commute" is a caused-and-effect claim a reader can follow; "OPTION A" is not.

## Failure mode 19b: failure mode 19 recurring on a diagram that predates the fix

**What happened.** The Social Proof principle's diagram (Salganik, Dodds & Watts, 2006, the MusicLab study) used a plain arc for "download count hidden" and a plain unfilled circle with a small dot for "download count shown" — the exact generic-primitive-with-no-silhouette pattern failure mode 19 already documents and fixes elsewhere. This diagram shipped in an earlier batch, before failure mode 19 was written up, and was never revisited once the rule existed. The user's catch, verbatim, circling the live diagram in a screenshot: "This is boring and not elegant... Root cause and fit same pattern across site." The diagram wasn't inaccurate (the arc and circle didn't misrepresent the study), it was illegible as *any specific thing* — a circle with a dot could mean anything, so nothing in the drawing itself said "a song on a download-count website," only the text labels did.

**The check.** Failure mode 19's own audit was a one-time pass over the diagrams that existed at the time it was written. It does not self-apply going forward: a diagram written before the rule existed, or one that slipped through that pass, stays broken until something prompts a second look. Whenever a diagram is flagged as "boring," "generic," "not elegant," or "could be about anything" in review, don't treat it as a new problem needing new taste — check it against failure mode 19's own test first ("cover every text label and look at the bare shapes alone: does each shape's silhouette suggest the specific real object, or could it be relabeled as anything with no change to the drawing?"). A generic circle, arc, or unfilled shape with only a label attached almost always fails this test.

**The fix, in practice.** Rebuilt the icon as a small phone/app-style mockup of the MusicLab site itself: a bordered frame with three song rows, each with a play-mark triangle, a track line, and a count chip that is an empty dashed placeholder when "hidden" and a filled bar (one exaggerated, colored terracotta) when "shown." This is the literal object the study used (a website listing songs with download counts), not an abstraction of "visibility." Two structural lessons from building the replacement, worth keeping for the next diagram built with a Python generator:
- **Compute every row's vertical position sequentially from the previous element's actual measured extent, never from a hardcoded per-row offset.** A first draft used a fixed `+224` offset to place the second (parallel) row, copied from the first row's approximate height. The two rows didn't actually take the same vertical space once real icon/outcome heights were filled in, so the second row's caption ended up overlapping its own outcome-bars chart, and the second row's outcome label rendered past the bottom of the `viewBox` entirely (silently clipped, invisible until screenshotted). The fix was a layout function that tracks a running `y` cursor and advances it by each element's real drawn height (icon extent, label height, arrow length, outcome extent) rather than a magic number restated per row.
- **Verify the diagram against the real site's actual CSS custom-property values, not a palette written from memory in an earlier document.** A first draft of the redesign used `ink #1E1B16` / `terracotta #B2472B` / `mustard #D9A441` (the values recorded in this project's own `CLAUDE.md`), but `mockup/styles.css`'s real `:root` block defines `--ink: #1B1E24`, `--terracotta: #C43E1F`, `--mustard: #E0A93A` — a different, though similar-looking, set of hex values. Rendering with the wrong palette would have shipped a diagram that doesn't match its own neighbors' colors. Always grep the live `styles.css` `:root` block for the actual current hex values immediately before generating any diagram SVG, rather than trusting a value recorded in a skill, a CLAUDE.md, or an earlier conversation.
- **When testing a redesign, splice it into a copy of the real page and screenshot the real component, not a hand-rolled preview shell.** A first verification pass built a standalone preview HTML with its own approximation of `.illustration`/`.bg-mustard` CSS, which is an extra place for a transcription mistake (wrong padding, wrong max-width) to hide. Copying the actual `principles.html` + `styles.css`, swapping only the target `<svg>` block via a regex scoped to that principle's own section (a regex with no section boundary matched the wrong principle's diagram once, since several principles share the same `viewBox` height by coincidence), and forcing that one `<details>` open, produces a screenshot of exactly what will ship.

## Failure mode 19c: fixing a generic icon by adding a whole new visual node, not just a better icon

**What happened.** Immediately after building the failure-mode-19b fix for Social Proof (a real song-list/phone icon replacing the generic circle+dot), a first draft additionally inserted a brand-new "outcome visual" node, a 4-bar chart or a crowd of person-dots, between the arrow and the existing outcome text label. The original diagram never had that node: it went icon → condition label → arrow → outcome label, four elements per row, nothing else. Adding a fifth element (plus its own gap-before and gap-after) pushed total diagram height from 464 to 679, a 46% increase, and the user's catch was immediate and specific: "These diagram are... too large and awkward looking. Need to be elegant and accurate but easy to see and interpret." The same instinct that makes failure mode 19's fix feel incomplete ("shouldn't there be more here to show the outcome?") is exactly what oversteps it — the outcome was already stated, in words, and didn't need a second, redundant visual restating it.

**The check.** Before finalizing any failure-mode-19 fix (or any fix prompted by "boring," "generic," or "not elegant" feedback), diff the new SVG's total node count and `viewBox` height against the original it's replacing. If the count or height grew, ask specifically: did I only improve the icon's own shape, or did I also add a new row, a new chart, a new divider, or a new caption the original didn't have? A silhouette-detail fix touches one shape. It does not add content.

**The fix, in practice.** Rebuilt all three Social Proof options at the exact original height (464) and exact original structure (icon → label → arrow → outcome-as-text), swapping only the icon shape itself (a phone/song-list mockup, a note+eye glyph, or a download-arrow+badge — three restrained options, each 2-6 path/shape elements). Two concrete guardrails to apply on every future fix of this kind:
- **Match the replaced element's own footprint.** If the generic shape occupied roughly an 80×88px area at a given center point, build the replacement inside that same area rather than letting it grow to accommodate more detail. A silhouette detail is 1-3 small marks (a handle, a perforation, a wrapper twist), not a fully separate composition.
- **A "does this look like the same diagram with a better icon, or a visibly bigger and busier diagram" gut check, done by literally overlaying or comparing the before/after `viewBox` heights, not by eye on a single screenshot** — the 46% height growth here wasn't obvious from looking at either version alone, only from the number comparison. Run that comparison as a standing step whenever a failure-mode-19 fix is drafted, not just when something already looks off.

This failure mode was caught before shipping (an in-flight fix on 7 other diagrams elsewhere making the identical silhouette-detail correction was checked against this exact rule mid-task and confirmed clean: all 7 held their original heights, and two icons that ran slightly over a restraint budget — more than ~3-4 extra elements to add silhouette detail — were trimmed back before shipping). Treat "does the height and node count match the original" as part of the failure-mode-19 fix itself, not a separate optional polish step.

## Failure mode 21: a two-condition icon distinguished by only one thin visual channel

**What happened.** Across two review rounds on the same redesign, two different icons (a note+eye badge, then a phone/song-list mockup) were each flagged for the identical underlying problem after looking, at a glance, like they should already have solved it. Round 1: the eye badge's only difference between "hidden" and "shown" was a diagonal slash line drawn over an otherwise-identical open/unfilled circle — user's catch: "It needs to be clearer distinction between each experience. It reads like just text." Round 2, on a *different* icon in the same set (the phone mockup, whose hidden/shown difference was just dashed-outline chips vs. filled chips): the identical complaint recurred almost verbatim. Both icons were individually reasonable-looking in isolation; the problem was only visible when comparing the two states side by side and asking whether a reader would notice the difference without already knowing which was which.

**The check.** Whenever a diagram encodes a two-condition comparison (hidden/shown, before/after, control/treatment) as two drawings of the same icon, count how many independent visual channels differ between the two states: line style (solid vs. dashed), opacity, fill vs. outline, hue/color accent, size, and count/quantity are the main ones available. **One channel is not enough**, even if that one channel is a clear, deliberate difference (a slash line is unambiguous on its own) — a reader scanning quickly registers "two icons, subtly different," not "condition A vs. condition B," until at least two channels move together in the same direction (e.g., dim + dashed for the "before" state, full-opacity + solid-fill + a color accent for the "after" state).

**The fix, in practice.** Every two-condition icon in the corrected Social Proof set now stacks three channels at once for the "revealed/shown" state relative to "hidden": full opacity (vs. ~0.32 dimmed), a solid fill accent in the site's terracotta (vs. an unfilled or dashed outline), and where there's room, an added mark (a corner flag, a filled pupil). None of these individually would have been enough on their own, per the two rounds of feedback that found the single-channel versions insufficient — it's the stacking that makes the states register as different experiences rather than a font-rendering variance. Apply the same opacity + fill-accent combination as the default starting point for any new hidden/shown, before/after, or control/treatment icon pair in this diagram system, rather than reinventing a one-channel difference each time. Watch the fill-accent channel against failure mode 7: a color accent must be a solid fill, never a stroke, on a `bg-mustard` diagram.

## Failure mode 22: a title with no type-scale distinction from the row labels beneath it

**What happened.** The same Social Proof redesign's title used font-size 14.5/weight 700 for its two-line heading, while the row condition-labels below it used 14/700 and the outcome labels used 15.5/700 — three text blocks within 1.5px of each other in size, identical in weight and family. Nothing in the typography marked the top two lines as *the header* versus just another label in the sequence. User's catch: "header needs to be more distinct."

**The check.** Read the diagram top to bottom and ask: could a reader, seeing only the rendered text sizes with no positional context, correctly guess which line is the title? If the title's font-size is within ~1-2px of the body labels' and shares the same weight, the answer is usually no.

**The fix, in practice.** Gave the title a real type-scale jump (16.5px/800 weight vs. the body labels' 14-15.5px/700 weight) plus a short centered rule beneath it (a decorative underline, ~48px wide, low-opacity ink) before the first icon begins. The rule is a separator, not new content, so it doesn't trip failure mode 19c's "don't add nodes" rule — it's a typographic/layout refinement of the existing title element, the same category of change as adjusting a font-size. Apply a real size/weight gap (at least ~2px and a full weight step, e.g. 700→800) between a diagram's title and every other text element in it as a standing rule, not just for this one diagram.

## Failure mode 9: a self-contained diagram can still make the reader do the connecting

**What happened.** Two further rounds of feedback landed on the *same three redesigned diagrams* after failure mode 8 was fixed — proof that per-node label specificity alone doesn't guarantee a diagram reads at a glance. Two distinct issues, both on diagrams whose individual node labels were already concrete and accurate:
1. **Loss Aversion's fan converge/diverge layout** (two starting conditions on the left, diagonal arrows crossing toward a shared middle node, diagonal arrows fanning back out to two outcomes on the right) forced the reader to *trace* which diagonal line connected which start to which end, especially where the two diagonals crossed near the middle node. The user's catch, verbatim: "seems like arrows and needing to connect dots in logic... should be self contained and self explanatory."
2. **Goal Gradient's pace comparison used a speedometer needle** (a semicircular arc with a needle at a shallow vs. steep angle) to represent "steady" vs. "picks up." Accurate as an abstraction, but a needle angle requires the reader to already know that gauges mean speed and that a steeper angle means faster — it names the outcome ("PACE PICKS UP" in the label) without the *icon itself* showing why. The user's catch, verbatim: "Pace change needs to be more evident."

**The check.** Two separate questions, both answered by the same method as failure mode 8 (cover the surrounding text, look at the diagram alone), but aimed at the connectors and the encoding rather than the node labels:
- **Connectors**: can a reader's eye follow any single path through the diagram (start → middle → end) without their finger, i.e. without needing to trace which of several crossing or converging lines belongs to which start point? If two or more arrows cross or merge before diverging again, the answer is no.
- **Encoding**: for any icon that represents a *difference in degree* (faster/slower, more/less, sooner/later), does the icon's own shape make that difference visible without reading its label — spacing, size, count, or fill extent that a reader would notice even in peripheral vision — or does it rely on an abstract dial, gauge, or arrow-angle convention the reader has to already know how to interpret?

**The fix, in practice.** For connectors: replace fan converge/diverge with parallel rows (see the updated fix under failure mode 8) — draw the shared state twice, once per row, so every row is one uncrossed, undiverged left-to-right line. It costs a little repetition; it buys a diagram nobody has to trace with a finger. For encoding a difference in degree: find a spatial property that *is* the mechanism, not a symbol for it. Goal Gradient's fix replaced the needle with a row of dots along a timeline toward a shared finish flag — evenly spaced for the steady card, spaced closer together (and drawn slightly larger, compounding the cue) approaching the flag for the pre-filled card — because "purchases happen more often as the reward gets closer" *is* the finding, and dot-spacing is a direct visual analogue of purchase frequency, not an arbitrary symbol standing in for it. Before reaching for a gauge, meter, thermometer, or arrow-steepness to show a rate or magnitude difference, ask what physically varies in the real phenomenon (spacing, count, size, fill) and encode that directly.

## Failure mode 10: a node with two visually identical sub-parts, referenced individually later

**What happened.** Loss Aversion's middle node drew "the same two jobs" as two identical blank rounded rectangles, accurately showing that the options were offered identically — but a later node's label ("KEEPS THE QUIET JOB") referred to one specific one of those two now-indistinguishable shapes. A reader had to trust the words rather than see which card was which; nothing in the drawing itself pointed back at a specific card. The user's catch, terse but exact: "Make clearer." Separately, Halo Effect's title, "ONE STRONG TRAIT, THEN EVERYTHING ELSE FOLLOWS," was evocative rather than concrete — it named that something follows without saying what, so it read as a tagline rather than a description of the mechanism, even though every node beneath it already was concrete. The user's catch: "Title doesn't self explain" (typo in original: "does self explain").

**The check.** Two related but distinct sub-checks: (a) if a node contains more than one instance of the same shape (two cards, two bars, two icons) and a *later* node's label singles one of them out by name, can a reader point at the specific instance being referred to without reading ahead first? If the instances are only distinguishable by position ("the left one") rather than by a visible property tied to what they represent, add a small in-shape label or accent naming each instance directly. (b) Does the diagram's *title* — usually the first thing read — already state the mechanism, or does it only gesture at one ("...then everything else follows," "...changes the outcome")? A title is a node like any other and is subject to the same self-containment bar as failure mode 8.

**The fix, in practice.** For (a): label each instance of a repeated shape with what specifically distinguishes it (Loss Aversion's fix: "JOB QUIET" / "JOB SOCIAL" printed directly inside each card), and carry the same accent color from a later outcome node back onto the specific instance it resolves to (the mustard accent on "JOB QUIET" matches the mustard checkmark that says "KEEPS THE QUIET JOB") so the connection is visible, not just readable. For (b): rewrite the title to name the actual mechanism in the same concrete register as the node labels beneath it — Halo Effect's fix, "ONE TRAIT COLORS RATINGS OF TRAITS NEVER TESTED," states what happens rather than promising that something does.

## Failure mode 11: an exaggerated-enough encoding still reads as subtle

**What happened.** Goal Gradient's first fix for failure mode 9 (dot spacing and size compressing toward a shared finish flag) was structurally correct — spacing and size *did* encode purchase frequency directly, not through an abstract dial — but the actual pixel differences (radius 3.2 to 5, gaps 30/24/18) were still close enough to each other that the "picks up pace" read as a mild variation rather than a clear signal at illustration scale. The user's catch, this time constructively specific rather than just "needs work": "Pace pickup is good but need to be more exaggerated" — confirming the *approach* from failure mode 9 was right and only the *degree* was insufficient.

**The check.** When an encoding is a difference in degree (size, spacing, count, fill), don't stop at "technically visible different values" — check whether the smallest and largest values in the range would still read as different from three feet away, or at the thumbnail scale failure mode 4 already warns about. If the answer is "you'd have to look closely," the range needs to widen, not just exist.

**The fix, in practice.** Widened Goal Gradient's dot radius range from 3.2–5 to 2.8–6.2 (more than doubling the smallest-to-largest ratio) and its gap compression from 30/24/18 to 34/26/12, and added a small motion-line mark beside the final, largest dot as a second, independent cue reinforcing the same read. When in doubt about whether a magnitude difference is exaggerated enough, push it further than feels proportionate — a diagram is read in seconds, not studied, and subtlety that would be tasteful in a data chart just reads as sameness here.

## Failure mode 12: a concrete title still uses an ambiguous word

**What happened.** Four rounds of feedback landed on titles that had already been rewritten once for failure mode 10b — proof that "concrete" and "unambiguous" are different bars, and that "unambiguous," "plain," and "specific" are three more. Loss Aversion's rewritten title, "SAME TWO JOBS, DIFFERENT STARTING POINT," named the mechanism in the abstract but left "starting point" open to a wrong reading: a viewer could take it to mean the two *jobs* had different starting conditions (start dates, entry points), rather than what it actually meant — the *person's* assumed-current situation differed between the two scenarios shown. The user's catch: "The title is ambiguous." Halo Effect's fix for failure mode 10b, "ONE TRAIT COLORS RATINGS OF TRAITS NEVER TESTED," used "colors" as a verb meaning "biases" or "influences" — but that diagram is full of literal color (mustard fill bars, terracotta accents), so "colors" sitting in the title primed a literal reading it didn't intend. The user's catch: "Colours in title is ambiguous." A round later, the word swapped in to fix that — "TRAITS NEVER TESTED" — drew its own complaint: "Never tested is ambiguous or too academic." "Tested" carries a research-methodology register that stood out against the plain-spoken rest of the diagram. Fixed to "TRAITS NOBODY CHECKED" — which drew a *fourth* complaint one round later: "Nobody checks is ambiguous. Be specific." The word "nobody" is grammatically passive and names no one — a reader can't tell whether "nobody" means no one in the world ever checked, some official process never checked, or specifically the person doing the rating never checked (the actual meaning). The user's own rewrite suggestion named the missing actor directly: "...traits that people hasn't even checked." Separately, Goal Gradient's "SAME 10 PURCHASES LEFT, TOLD DIFFERENTLY" had the identical structural problem — "told differently" doesn't say who tells or who's told — caught in the same round once the pattern was pointed out.

**The check.** Four distinct ways a title (or any node label) can still be wrong even after it states a mechanism concretely and unambiguously: (a) a phrase whose referent isn't pinned down — could this wording apply to more than one thing in the diagram (the jobs vs. the person, the card vs. the purchase, the trait vs. the trait-rating)? (b) a word with a literal, visual meaning that the diagram itself contains as an actual visual element (color, size, direction, weight) — using that word figuratively right next to the literal thing invites a double-take. (c) a word that is technically clear but breaks register — more formal, academic, or clinical than the rest of the diagram's language. (d) passive or agentless phrasing — "nobody checked," "told differently," "was decided," "gets rated" — that describes an action without naming who performs it, leaving the reader to supply an actor that may not be the right one. Check every noun and verb in a title against all four: does it point at exactly one referent, does it avoid colliding with a literal visual element, would it sound natural said aloud next to the diagram's other labels, and — for every verb — is its subject named rather than implied?

**The fix, in practice.** For (a): replace the ambiguous phrase with the specific thing it was standing in for — Loss Aversion's fix dropped "starting point" entirely and named the actual mechanism plainly: "THE JOB LABELED &quot;CURRENT&quot; IS THE ONE THEY KEEP." For (b): replace the pun-risk word with a synonym that has no literal reading in this diagram's visual vocabulary — Halo Effect's fix replaced "colors" with "sets the score." For (c): match the title's word choice to the plainest phrasing already used elsewhere in the same diagram rather than inventing new vocabulary. For (d): rewrite the passive construction as an active sentence with a named human subject — Halo Effect's fourth fix, "ONE TRAIT CHANGES HOW PEOPLE SCORE TRAITS THEY NEVER CHECKED," names "people" as the ones both perceiving the one trait and failing to check the rest, closing the "checked by whom" gap the passive left open. When a caption elsewhere in the same diagram uses the same passive construction, fix it too for consistency rather than leaving the title and caption disagreeing in register. Read the rewritten title once more as if meeting the diagram cold: hunt for any word that could mean something else here, that sounds more formal than the diagram's own voice, or that describes an action with no stated actor, before considering the title finished. (Goal Gradient's own attempt at fix (d), naming "customers" as the actor, is the worked example for failure mode 13 below — naming the actor fixed the passive-voice problem but introduced a factual one, because the verb chosen for that actor was itself wrong.)

## Failure mode 13: an active, unambiguous verb that still misattributes the mechanism

**What happened.** Goal Gradient's failure-mode-12(d) fix, "CUSTOMERS TOLD THEY'RE CLOSER BUY THE SAME 10 FASTER," passed every check in failure mode 12: it named an actor, avoided a pun, matched the diagram's register. It was still wrong. The word "told" describes an explicit act of communication — someone or something informs the customer. But the actual cited mechanism (Kivetz, Urminsky & Zheng, 2006) is perceptual: a loyalty card pre-filled with 2 stamps creates a felt sense of progress purely through its visual design; nobody tells the customer anything. The site's own article text for this principle already said so in so many words — "Perceived proximity to completion, not just objective distance, drives the acceleration" — and the diagram's own caption already said "felt closer." The title was the one place still describing the wrong kind of event. The user's catch, precise and self-correcting: "But in this case, they're not told. They perceive they're closer."

**The check.** This is a different axis from every check in failure mode 12 — those are about whether a word is *clear*; this is about whether a clear word is *true to the mechanism*. Behavioural economics principles very often turn on exactly this distinction: an effect works *because* nothing is explicitly communicated, and a perceived or inferred cue does the work instead (contrast with a principle that genuinely does hinge on an explicit disclosure or message, where "told" or "shown" would be correct). Before finalizing any verb that describes how a belief, feeling, or perception forms in a diagram's subject, ask: does the cited study's mechanism involve someone being informed of something (told, shown, warned, notified), or does it involve someone inferring or perceiving something from an ambient cue with no explicit message attached (perceives, feels, reads as, experiences)? Check the verb against the principle's own "The psychology" paragraph and its citation excerpt, not just against how natural the sentence sounds.

**The fix, in practice.** Swap the communication-verb for the correct perception/inference-verb (or vice versa, if the direction of the error runs the other way) — Goal Gradient's fix: "told they're closer" became "who perceive they're closer," landing on "CUSTOMERS WHO PERCEIVE THEY'RE CLOSER BUY THE SAME 10 FASTER." Notice this diagram's own caption ("felt closer") and its article's psychology section ("perceived proximity") had already used the correct verb family — when a title's verb disagrees with the mechanism-describing language already written elsewhere for the same principle, that disagreement is itself a signal worth checking before assuming the newer wording is the accurate one.

## Failure mode 14: legible in a full-page screenshot, illegible on a real phone

**What happened.** The entire 48-diagram set (and the first anchoring redesign after it) used a two-column layout — icon+label in a ~100-140-unit-wide left column, arrow, outcome in a ~100-140-unit-wide right column, inside a fixed `viewBox="0 0 400 300"`. Failure mode 4's screenshot review caught text collisions, but every screenshot was taken at a fixed pixel width chosen for review convenience, not measured against a real phone. On an actual 375px-wide mobile viewport, the `.illustration` box's real CSS width was only ~263-310px, so the 9.5-unit label text (already the smallest text in the diagram) rendered at 5.9-7.6 *real* pixels — below normal reading size, requiring pinch-zoom to read. The user's catch, verbatim, pointing at a live shipped diagram: "on mobile they requires a pinch and zoom. Redesign and adjust all so that on mobile they can be seen without zoom." A second, compounding bug: the CSS `.illustration` box forced a fixed `aspect-ratio` (16:9, later 4:3) on mobile that didn't match the SVG's own `viewBox` aspect ratio, letterboxing the actual artwork into an even smaller area than the box itself.

**The check.** A full-page or even per-element screenshot at an arbitrary pixel width never answers "is this legible on a phone" — only a real pixel measurement at a real mobile viewport width does. Before considering any diagram finished, load the actual page in Playwright at `viewport: {width: 375, height: ...}` (no artificial zoom), force-open the `<details>` if the illustration sits inside one, get the `.illustration` element's real `boundingBox()` width, then `element.evaluate()` to read every `<text>` node's real `getBoundingClientRect().height` in that context. If the smallest reported height is under roughly 9px, the diagram will require pinch-zoom on a real phone, full stop — no amount of "it read fine in the screenshot" overrides that measurement.

**The fix, in practice.** Two independent fixes, both required:
1. **CSS**: never force a fixed `aspect-ratio` on the `.illustration` box on mobile. Instead let the `<svg>` size itself intrinsically — `<svg width="100%" role="img" ...>` with **no `height` attribute at all** (an explicit `height="100%"` forces the outer box's shape onto the SVG and then letterboxes the viewBox content via `preserveAspectRatio`, wasting space) — paired with `.illustration svg { display:block; width:100%; height:auto; }` in CSS, so the rendered height is always computed from the SVG's own `viewBox` ratio with zero letterbox waste, on any box width, for any future diagram's shape.
2. **Layout**: replace the two-column layout with a single centered column using nearly the full viewBox width per row (icon → label → arrow → outcome, stacked top to bottom), and grow the `viewBox` height per diagram rather than trying to fit more into a fixed 400×300 canvas. A first instinct — "just scale the whole canvas up" — is a mathematical no-op: uniformly rescaling the viewBox dimensions, every coordinate, and every font-size by the same factor changes nothing about the final rendered pixel size, because rendered size is set by the font-size number's *fraction of the (fixed real-world) box width*, not by the viewBox's absolute units. The only real fix is genuinely larger font-size numbers relative to the box, which requires more usable width per line of text — hence the column change, not a scale change. The shipped mobile-legible template (title 14.5-15, condition labels 14, hero stat numbers 21, secondary/caption text 12.5) measures 9-15 real CSS pixels at 375px viewport width, vs. the old template's 4.3-7.6px — verify any new diagram against those numbers, not against the old template's font-size values.

## Failure mode 15: an icon and the label below it overlap because the gap doesn't account for text ascenders

**What happened.** The single-column template's row layout (icon centered at a fixed offset, then a fixed vertical advance before the next label) computed that advance using only the icon's nominal radius plus a small constant gap — it didn't account for the fact that an SVG `<text>` element's `y` attribute is its *baseline*, and a 14-unit-font-size label's letterforms extend roughly 10 units *above* that baseline. For icons whose stroke sits right at their outer radius (an outlined circle, an eye icon, a card's rectangle edge, a speech bubble's tail), the label's letters started only 3-4 units below the icon's actual bottom edge — comfortably less than the ~10-unit ascender height — so the top of the label text visually overlapped the bottom of the icon. It was barely visible on solid-fill icons (a filled checkmark circle) because the overlap fell on empty space inside the disc, but clearly visible — text literally crossing through the icon's outline — on every outline icon, both eye icons, every card, and the speech-bubble's tail, which extends further than any circular icon. The bug shipped in the first two batches of the mobile-legible redesign before being caught.

**The check.** For any node in an icon-then-label chain, compute (or measure) the icon's actual vertical extent *below its own center point* — not its nominal radius, its real drawn bottom edge, including tails, ticks, or asymmetric elements like a speech bubble's pointer. Then check: does the label's text-top (baseline position minus roughly 0.7× the label's font-size, for a rough ascender estimate) sit clearly below that icon-bottom, with a visible gap — not just numerically non-negative? A 2-4 unit gap between "icon bottom" and "text baseline" is not a real gap once the ~10-unit ascender is subtracted from the baseline; the number that must be positive is (baseline − ascender) − icon-bottom, not baseline − icon-bottom.

**The fix, in practice.** Pass each icon's true half-height into the row-building function explicitly (or default to the tallest icon in the shared icon library, so a smaller icon just gets slightly more breathing room rather than any icon risking collision) and compute the advance as `icon_center_offset + icon_half_height + gap + ascender_buffer` — not a single flat constant that only happened to work for the icons tested first. After changing this kind of shared spacing constant, re-render and re-screenshot *every* diagram already built with the old constant, not just new ones — the bug is in the generator, so every diagram that used it inherited the defect, even ones that were already reviewed and shipped under the old (insufficient) gap.

## Failure mode 16: a real, correctly-cited number that isn't the study's actual headline result

**What happened.** The Tradeoff Transparency diagram (Buell & Choi, 2025, a field experiment inside Commonwealth Bank of Australia's credit card funnel) used "FEWER LATE PAYMENTS" as its headline outcome — a real finding, taken word-for-word from one of the principle's own excerpt blocks ("Customers who saw each card's drawbacks before choosing went on to make late payments less often..."). But the same section's own `result-table` — sitting in the same file, a few hundred lines above where the diagram draws its data from — reports the study's actual two headline numbers: monthly spend **+9.9%** and cancel rate **−20.5%**, with the article's own `flow-insight` line stating plainly that customers "spend more, cancel less, and make late payments less often" — spend and cancellation named first, late payments last, and the excerpt about late payments is explicitly framed as a secondary reassurance ("the gains in engagement and retention did not come at the expense of customers' financial well-being"), not the primary result. The diagram wasn't citing a fabricated number — every word was real and accurately quoted — but it promoted a secondary caveat to the position of headline finding, while the real headline (the two numbers with an actual reported percentage, sitting one scroll away) never made it into the diagram at all. The user's catch, verbatim, pointing at the shipped diagram: "This ain't the key findings. It's about increase retention and higher spend?"

**The check.** Before finalizing any diagram for a principle whose citation includes a `study-card` with a `flow-diagram`/`result-table` (the "Experiment Teardown" component used across the batch-A-and-later principles that build on a real field experiment), read that result table and its `flow-insight` line *first* — before drawing anything, and even before reading the shorter `excerpts` paraphrase blocks. The result table is the study's own headline numbers, in the order the study itself reports them. If the diagram's chosen outcome doesn't match the first-listed row(s) of that table, ask specifically: is what I'm about to draw the *primary* finding, or a secondary point mentioned to preempt an objection ("...and this didn't come at a cost")? A true statement pulled from deep in the excerpts can still misrepresent the study's own emphasis if it isn't the number the study itself led with.

**The fix, in practice.** Rebuilt with the real result-table numbers (+9.9% monthly spend, −20.5% cancel rate) as the two outcome rows; the late-payments point was dropped from the headline (it can still appear in a caption or mechanism-note as a secondary, correctly-framed reassurance, but not as a row's primary hero stat). The general rule this generalizes to: when a principle's citation includes both a short paraphrased-excerpt block *and* a structured result table/teardown elsewhere in the same file, the table is the more authoritative source for "what is the headline finding" — excerpts are written to be readable prose and don't always preserve which result was primary vs. secondary in the original study.

## Failure mode 17: a stale placeholder caption survives right next to a now-real diagram

**What happened.** Every principle's markup was originally templated with a `<p class="caption">Awaiting a real example: ...</p>` paragraph directly under the `.illustration` div — a genuine, intentional content slot inviting the site owner to later add a real personal photo example (one principle, Scarcity, already has this filled in as `<p class="caption">A real example: ...</p>`). But every diagram-building pass across every session of this skill's use — including the full mobile-legibility redesign that rebuilt all 56 diagrams with real citation-backed content — only ever read and replaced the `.illustration` div itself, never the adjacent `.caption` paragraph one line below it. The result: 50 of 56 principles shipped with a fully-researched, citation-grounded mechanism diagram sitting directly above a caption that says, in effect, "there's no real content here yet" — actively contradicting the diagram right above it. The user's catch, pointing at a live shipped page: "You need to find where it references this placeholder type comment and remove."

**The check.** This bug doesn't live inside the SVG, so no per-diagram screenshot or pixel measurement catches it — it requires checking the markup *around* the diagram, not just the diagram itself. After building or replacing any principle's `.illustration` div, check the very next sibling element: if it's `<p class="caption">Awaiting a real example: ...</p>`, that caption is now stale scaffolding, not real content — the diagram it once excused the absence of now exists. This is a structural check to run once per principle touched, and (as this incident showed) worth an occasional full-file sweep (`grep -c "Awaiting a real example"`) even outside an active diagram-building session, since the drift between diagram and caption accumulates silently across sessions with nothing to trigger noticing it.

**The fix, in practice.** Delete the stale `<p class="caption">Awaiting a real example: ...</p>` paragraph whenever the diagram immediately above it is real (has a citation, isn't a stub). Leave alone any instance already filled in with a genuine real-world example (`<p class="caption">A real example: ...</p>`, no "Awaiting") — that's the slot doing its intended job, not scaffolding. The general lesson: a batch process that touches one element (the diagram) but not its structurally-adjacent sibling (a caption written to describe the diagram's *absence*) will silently let the two drift out of sync — when redesigning or rebuilding one part of a templated block, check whether other parts of that same block were written assuming the old state and now need updating too, not just the part the task nominally asked for.

## Failure mode 18: a domain-accurate diagram still requires knowledge the reader doesn't have

**What happened.** The Law of Round Numbers diagram (Pope & Simonsohn, 2011: baseball batters finish seasons at .300 far more often than .299, plus a parallel SAT-retesting finding and a lab study) was built by copying the Decoy Effect diagram's proven two-row A/B-box layout and relabeling the boxes ".299" and ".300". Every mechanical check passed: valid SVG, no text collisions, correct contrast, mobile-legible font sizes, a real cited number ("nearly 4x"). It still shipped broken, because a reader who doesn't already know that a baseball batting average around .300 is a meaningful, memorable threshold has no way to tell *why* two decimal numbers in boxes matter, or why one box is highlighted and the other isn't. The diagram was accurate to the citation and illegible to anyone without that specific piece of outside domain knowledge. The user's catch, verbatim: "Super abstract... needs to be easier to understand and self-contained and not require other knowledge."

**The check.** This is a different axis from failure mode 8 (which catches a node whose meaning depends on reading the *surrounding caption text*). This one catches a node whose meaning depends on the reader already possessing *outside domain knowledge* the diagram never supplies, a sports league's scoring conventions, an industry's benchmark figures, a specific culture's frame of reference. Before finalizing, imagine the specific reader this site is actually for (a product/commercial audience, not a subject-matter enthusiast) meeting the diagram cold: does every number, unit, or named quantity in it carry its own meaning visibly, or does "why this number matters" live only in prior knowledge the diagram assumes but never states? A bare decimal, score, or metric sitting in a box is not self-explanatory just because it's accurately transcribed from the study, arithmetic or scale conventions that are obvious to insiders (a .300 batting average, a "good" Net Promoter Score, a par score in golf) are exactly the kind of fact a diagram must either explain within itself or avoid leaning on.

**The fix, in practice.** Two complementary moves, used together on the fix: (1) if the citation covers more than one real-world domain (as this paper does: baseball, SAT scores, and a lab study), prefer the domain whose numbers are self-interpreting to the widest audience, a test score of 990 sitting 10 points below a round 1000 needs no domain expertise to read as "nearly there," where a .300 batting average requires already knowing the sport's scale. This is a legitimate curatorial choice, not a suppression of the more sport-specific finding, which can still be fully reported with its own real citation in the "Key findings" section. (2) Encode the actual general mechanism spatially rather than leaning on two isolated labeled boxes: a real number line with the round number marked at the center and the two comparison values placed at equal, visible distance on either side makes "these are the same distance from round, only one side reacts differently" readable from the drawing alone, with no caption and no outside knowledge required. The same self-containment audit applies to the article's own prose, not just the diagram: check whether "The psychology" paragraph opens with the same domain-specific fact cold (this principle's did, leading with "a batting average of .299 and .300" before ever explaining the general mechanism) — restructure so the general, universally-graspable version of the mechanism comes first, with the domain-specific study cited afterward as "an unusually clean real-world example," not as the reader's entry point.

## Failure mode 19: the right object, correctly labeled, drawn as a generic geometric primitive

**What happened.** The Salience diagram's redesign (fixing failure mode 8's abstract "A"/"B" boxes) correctly identified the object the cited study's mechanism actually needs, two identical lottery/raffle tickets at the same odds, and correctly labeled both "50%." Every check up to that point passed: real object, correct quantity, self-contained, no outside domain knowledge required. It still shipped wrong, because the tickets were drawn as plain rounded rectangles (`<rect rx="5">`) with a dashed line down the middle. Nothing about that shape is specific to a ticket, it's a shape any labeled container could use. Only the "50%" text told the reader it was a ticket; the silhouette itself read as an interchangeable box. The user's catch, verbatim, pointing at the shipped diagram: "These diagram just look like blocks. Do better. Make them look like what they are not just blocks."

**The check.** This is a different axis from failure mode 2 (which catches drawing the *wrong* object) and failure mode 8 (which catches a node whose *meaning* depends on outside text). This one catches the right object, correctly labeled, rendered with a shape that has no visual feature distinguishing it from any other labeled box. Before finalizing any icon or shape meant to represent a specific physical object, cover the text label inside or beside it and ask: does the bare outline alone, with no words, suggest this specific object, or could the identical shape just as easily be relabeled to represent something else with zero change to the drawing? A plain rounded rectangle, a plain circle, or a plain rounded-corner card are all "could be anything" shapes, they carry no silhouette cues of their own.

**The fix, in practice.** Give the shape the one or two silhouette details that make the real object recognizable without reading the label, not a fully rendered illustration, just the detail a person's eye actually uses to identify the object at a glance. A ticket gets the punched-notch cutouts at its tear-perforation (two small circles filled in the background colour, positioned where the dashed tear line meets the shape's outer edge, so it reads as a physical cut rather than a decorative line). A coffee cup gets a handle and a lid seam, not a plain circle. A receipt gets a zigzag torn bottom edge, not a straight-edged rectangle. The detail should sit at the object's most recognizable silhouette feature, the one place a reader's eye would check first to identify it, not scattered decoration. Re-run the "cover the label" test after adding the detail: if the shape still needs its text to be identified, the detail chosen wasn't the load-bearing one, try a different feature of the real object instead of adding more decoration to the same one.

## Failure mode 20: a newer diagram quietly reverts to the pre-redesign giant-panel-box layout

**What happened.** Five principles built after the 56-diagram mobile-legibility rollout (Precommitment Devices, Crossmodal Correspondence, Meaningless Differentiation, Licensing Effect, Present Bias) and both `.illustration` diagrams inside `mockup/science-behind.html`'s dual-lip-coffee-cup entry (the rim, the glaze) were drawn from scratch without the established icon-plus-label chain structure. Instead each used two (or three) giant `<rect fill="rgba(255,255,255,0.08)" rx="10">` panels roughly 340×150-164px each, stacked with a dashed divider between them, each panel holding a centered title, a small icon or tiny colored swatch, and an outcome line, with a viewBox height as tall as 400×540. This is exactly the "abstract chart that needs the caption to make sense" and "giant background panel" pattern the mobile-legibility redesign (failure mode 8, and the whole point of the icon-plus-label chain fix) had already moved away from for all 56 original diagrams. Every one of the pre-existing checks below still technically "passed" on these seven (real cited object, correct numbers, no unevidenced claims, no mustard-background contrast violation) because none of those checks test for panel bulk specifically. The user's catch, verbatim, after seeing two of these live on the site: "Illustrations not elegant like we've been building and take too much room in mobile and not clear. Desktop takes FAR too much space." A same-page comparison made the regression obvious: the pilot diagrams (Loss Aversion, Halo Effect, Goal Gradient) and the bulk of the 56-diagram rollout use a single centered column, no background panels at all, one compact icon per row directly on the `bg-*` field, connected by a short arrow to a bold outcome line, typically landing at viewBox height 440-506; the five newer principles and both Science Behind diagrams instead used the older comparison-box idiom this skill's own failure-mode-8 fix was written to retire.

**Why the existing checks missed it.** This skill's per-diagram checks (the question list below, and failure modes 1-19) are all about *content correctness and legibility of what's drawn* — right citation, right object, right contrast, readable at mobile scale, self-contained meaning. None of them ask *how much chrome the layout itself adds around that content*. A diagram can cite the right study, use the right object, pass every contrast and self-containment test, and still be bulkier and less elegant than it needs to be because it wraps each comparison in a decorative background rectangle that adds visual weight without adding information. This is a structural/layout regression, not a content-accuracy one, and it can reappear specifically whenever a diagram is built for a newer principle or for a different page (like `science-behind.html`) where the person building it doesn't have the pilot diagrams' markup open side by side as a literal template.

**The check.** Before finalizing any new `.illustration` diagram, or before extending this pattern to any other page, open one of the three original pilot diagrams (`mockup/principles.html#loss-aversion`, `#halo-effect`, or `#goal-gradient`) and compare structure line by line: is there any `<rect>` in the new diagram wider than roughly 60px that isn't a small icon shape (i.e. a background panel, card, or box wrapping a whole row of content)? If yes, that's this failure mode. The pilots and the bulk of the 56-diagram rollout have zero such rects — every row is icon, label, arrow, outcome, directly on the `bg-*` field with no enclosing shape.

**The fix, in practice.** Rebuild the diagram as a single-column chain: title (one or two lines) → icon (a small, recognizable shape per failure mode 19, not a panel) → bold label → arrow (line + chevron, matching the pilots' exact arrow markup) → bold outcome line, colored with the diagram's one accent when it's the notable/counterintuitive result → optional one-line italic subcaption for a fact that rules out a confound (same temperature, same price) → a dashed full-width divider (not a boxed panel) → the mirrored second row → a final one- or two-line italic caption stating the takeaway. For a three-way comparison (more than two rows), don't gutter each row into a panel to fit it, compress instead: a short label, an inline mini visual proportional to the actual comparison (e.g. a horizontal timeline with dots placed at the real day-counts, rather than three separate numbered circles inside a boxed card), and a one-line outcome, repeated three times with dashed dividers between. Confirm the fix worked by measuring: the rebuilt diagram's viewBox height should land in the same 400-510 range the pilots and the bulk of the rollout use, not 520+, and a `fill="rgba(255,255,255,0.08)"` (or any comparably large panel-fill) grep across the file should return zero matches after the fix. This same discipline applies the moment `principle-mechanism-diagram`'s pattern is reused on a different page (Science Behind, a future page) — the "which page" changes nothing about which layout to use; there is exactly one correct `.illustration` layout on this site, and it's the pilots' single-column chain, never a page-specific variant.

## Failure mode 19d: a comparison encoded as an unlabeled grid of colored squares

**What happened.** The Diversification Heuristic diagram (Benartzi & Thaler, 2001: investors splitting a fund menu roughly evenly across however many options it lists) drew "tap 4 of 10 options" and "tap 5 of 10 options" as two 5×2 grids of plain colored squares, four (then five) filled mustard, the rest outlined, with no other shape variety anywhere in either icon. This is failure mode 19's exact test failing in its purest form: covering the "TAP 4 OF THE 10 OPTIONS" label and looking at the bare grid alone, the squares could be a color palette, a calendar, a game board, or a seating chart, nothing about the shape says "an investing app's menu of fund options," even though the same principle's own "Spotted in the wild" block, a few hundred lines below in the same file, already shows the literal real object (CommSec Pocket's "Invest in" list) this diagram is meant to depict. The owner's catch, verbatim, pointing at the live diagram: "This doesn't explain well or narratively the illustration." Unlike failure mode 19's original ticket example (a real object drawn as a primitive shape, rescued by adding a tear-notch), this diagram's underlying object was never drawn as itself at all, ten interchangeable squares stand in for "a scrollable list of named menu rows," a fundamentally different silhouette, not a close miss needing one added detail.

**The check.** When a diagram's core comparison is "N of a menu's items get selected/tapped/chosen," ask whether the chosen shape for "the menu" is a generic array (a grid of identical squares, dots, or bars with no frame, no orientation, no context) or a recognizable rendering of the actual UI surface the study or screenshot shows (a list inside a bordered screen, ordered top-to-bottom, not a grid). A grid of colored squares reads as an abstract proportion chart (like a waffle chart), which is a legitimate way to show *a percentage* but not a legitimate way to show *a menu of options being individually selected*, those are different claims, and this site's own principle explicitly makes the second one, not the first.

**The fix, in practice.** Rebuilt both icons as a compact phone/app-list mockup: a bordered rounded-rect frame with a small notch at the top edge (establishing "this is a phone screen," the same phone-notch device used elsewhere on the site's other icon systems), containing ten thin horizontal rows stacked top to bottom, exactly matching the vertical list layout of the real CommSec Pocket screen shown lower on the same page, with the tapped count filled solid mustard and the rest left as a thin outline, same fill/outline channel the original squares already used, just applied to a shape that now reads as "a scrollable list on a phone" without needing the label at all. Kept the same footprint and did not add a new node, per failure mode 19c, the fix reused the exact vertical space already sitting empty between the old squares and the "TAP N OF THE 10 OPTIONS" label, so the diagram's total height didn't grow. A trailing wording bug was caught in the same pass: the caption ("Only how many tiles got tapped did") still said "tiles," a leftover from the old square icon, updated to "rows" to match the new shape once it stopped being tile-shaped.

**Cross-check performed.** A grep for the same repeated-small-square signature (`rx="2.5"` in clusters of 6+) across every principle in the file found exactly one instance, this diagram, so the bug isn't a wider pattern from the same authoring pass. A visual spot-check of the five other most-recently-added principles at the time (Bundling, Clawback, Disclosure Backfire, Propinquity Effect, Availability Heuristic) found each already uses a recognizable, distinguishing shape (a briefcase, a speech bubble, a bar-chart glyph, doors with knobs) rather than a generic primitive, so this was an isolated miss on one diagram, not a rollout-wide regression like failure mode 20's five-principle giant-panel-box lapse. Worth re-running this same spot-check (cover the label, does the bare shape suggest the specific object) on future newly-added diagrams rather than assuming failure mode 19's original audit still covers everything added after it.

## Failure mode 23: a count comparison encoded only as "how many of these small marks are filled in"

**What happened.** Failure mode 19d rebuilt the Diversification Heuristic diagram's two icons as a recognizable phone/app-list mockup (fixing the "generic grid of squares" problem), but kept the underlying comparison exactly as it was: "4 of 10 thin rows filled mustard" vs. "5 of 10 thin rows filled mustard," the two icons differing by exactly one 4.52-unit-tall bar out of ten. The object was now recognizable (failure mode 19 satisfied), the comparison was still nearly invisible, because the actual thing being compared, a count difference of one, was encoded purely as "one more thin bar happens to be filled," and a reader has to count carefully across two separate icons to notice that. The owner's catch, verbatim, pointing at the live (already-rebuilt) diagram: "This is narratively clear[,] different between the options" (i.e. it wasn't). This is a distinct failure from 19d: 19d is about the *shape* being unrecognizable; this one is about the *count itself* being unreadable even once the shape is fixed, because "count" was never given its own visual weight, only a label sentence ("TAP 4 OF THE 10 OPTIONS") already carried the number, and the icon didn't reinforce it.

**The check.** Whenever a diagram's core comparison is a count or quantity difference (N of M selected, N vs. M items, a tally), ask: if a reader covers every text label and looks only at the two icons side by side, can they tell *which one has more* without counting individual marks? Counting past two or three identical small elements is slow and error-prone at illustration scale, exactly the kind of thing failure mode 11 already warns will "read as subtle" even when the underlying values are technically different. A count encoded solely through incremental fill among many identical small marks fails this test almost by construction, the visual difference between "4 filled" and "5 filled" out of ten is one thin sliver, regardless of how well-drawn the marks themselves are.

**The fix, in practice.** Add a large, unambiguous numeral badge directly on (or overlapping the corner of) each icon, exactly the size and weight of the diagram's other "hero" numbers (this site's established hero-stat scale, `font-size` in the low-20s, `font-weight` 800, per failure mode 14's mobile-legible template), not the diagram's small label-text scale. A solid-filled circle in the diagram's accent color with the count as its numeral, positioned like a real app's notification-count badge on the icon it belongs to, reads instantly without requiring the reader to count anything, matches failure mode 21's "stack channels" principle (the badge is a second, independent channel on top of the existing fill-count encoding, not a replacement for it), and costs no new row or node per failure mode 19c, since it's an overlay on an existing icon, not a new step in the chain. This is the general fix for any future diagram whose core finding is "N of M," not just this one: draw the count as a number, not just as a quantity of filled marks.

## Before drawing anything: the nineteen-question check

For every mechanism diagram, answer these in order, in writing, before opening the SVG:

1. **What is the principle's seminal citation, and what exact sentence(s) from its excerpt am I illustrating?** (Not the site's own experiment, unless the diagram is explicitly for the experiment page.)
2. **What are the literal real-world object, setting, and quantities that citation used?** (Not a generic or rounder stand-in.)
3. **For every arrow, callout, or label that implies a claim — where in the article text or citation excerpt does that specific claim appear?** If nowhere, either research it properly or don't draw it.
4. **Does any number in the diagram belong to a reference point, anchor, or "current state" that is not itself one of the options being compared?** If so, check it against failure mode 6 before finalizing — either the numbers need to actually match something else in the diagram, or that reference needs to drop numeric precision and state only the qualitative direction the mechanism depends on.
5. **On a `bg-mustard` diagram, is any text, thin stroke, or unfilled outline colored terracotta or teal?** If so, check it against failure mode 7 — convert it to ink; only large solid-filled shapes may stay terracotta/teal on mustard.
6. **Cover the caption and mechanism-note: does the diagram alone still explain what happened, to whom, and why?** If any node's meaning depends on reading outside text, check it against failure mode 8 — rebuild that node as an icon-plus-concrete-label step in the chain rather than an abstract shape. This includes the title itself, per failure mode 10b.
7. **Does any arrow cross or converge with another before diverging again?** If so, check it against failure mode 9 — redraw as parallel rows instead of a fan, even if it means repeating a shared node.
8. **Does any icon represent a difference in degree (faster/slower, more/less) using an abstract dial, gauge, or angle instead of a spatial property that directly mirrors the real phenomenon?** If so, check it against failure mode 9 — re-encode using spacing, count, size, or fill extent that visually is the difference, not a symbol for it.
9. **Does any node contain two or more visually identical sub-shapes that a later node's label refers to individually?** If so, check it against failure mode 10a — label each instance directly and carry a shared accent color from the instance to the outcome node it resolves to.
10. **For every degree/magnitude encoding already in the diagram, would the smallest and largest values still read as clearly different at illustration scale, not just on close inspection?** If it's a close call, check it against failure mode 11 — widen the range further than feels proportionate.
11. **Read the title (and every node label) once more as a stranger meeting the diagram cold: does any word have more than one plausible referent, a literal visual meaning (color, size, direction) that the diagram also contains as an actual element, a more formal/academic register than the diagram's own caption and labels, or a passive/agentless verb that doesn't name who performs the action?** If so, check it against failure mode 12 — swap the word for one with exactly one reading in context, ideally reusing a phrase the diagram's own text already uses elsewhere, and rewrite any passive construction with a named human subject.
12. **For every verb describing how a belief, feeling, or perception forms in the diagram — does the cited study's mechanism actually involve someone being informed of something, or someone inferring/perceiving something from an ambient cue with nothing communicated?** If the verb doesn't match, check it against failure mode 13 — check it against the principle's own "The psychology" paragraph and swap for the mechanistically accurate verb family (told/shown/informed vs. perceives/feels/infers).
13. **Measured at a real mobile viewport (Playwright, `viewport: {width: 375}`, no zoom), is every `<text>` element's real rendered height at least ~9px?** A full-page or fixed-width screenshot cannot answer this — only a `getBoundingClientRect()` measurement inside the actual mobile-width page can. If any text measures smaller, check it against failure mode 14 — the fix is a wider single-column layout with genuinely larger font-size-to-viewBox-width ratios, not a uniform rescale (which is a no-op) and not a smaller `viewBox`.
14. **For every icon-then-label pairing, does the label's text-top (baseline minus roughly 0.7× font-size for the ascender) sit clearly below the icon's true drawn bottom edge — tails, ticks, and asymmetric elements included, not just its nominal radius?** If the gap is thin enough that it only works out to a positive number before subtracting the ascender, check it against failure mode 15 and widen the spacing constant for every icon type, not just the one currently failing.
15. **If this principle's citation includes a structured `result-table`/`flow-insight` teardown elsewhere in the same file, does the diagram's chosen outcome match that table's first-listed, headline number(s) — not just any true statement found in the shorter excerpt blocks?** If the diagram's outcome is a secondary or reassurance point ("...and this didn't come at a cost") rather than the study's actual primary result, check it against failure mode 16 and rebuild from the result table's own numbers.
16. **Is the element immediately after the `.illustration` div a `<p class="caption">Awaiting a real example: ...</p>`?** If so, and the diagram above it is real (cited, not a stub), check it against failure mode 17 and delete that stale caption — it now contradicts the diagram sitting right above it.
17. **Does understanding any number, unit, or named quantity in the diagram depend on outside domain knowledge the diagram never supplies** (a sport's scoring scale, an industry benchmark, a culture-specific reference point), **rather than something visibly explained by the drawing itself?** If so, check it against failure mode 18: if the citation covers more than one real-world domain, prefer whichever is self-interpreting to the widest audience for the diagram itself (the more specialized finding can still be fully cited in "Key findings"), and encode the actual comparison spatially (e.g. a number line with the round/reference point marked and both compared values placed at their real, visible distance from it) rather than two isolated labeled boxes. Apply the same audit to the article's own opening "The psychology" sentence, not just the diagram: does it lead with the same domain-specific fact cold, or does the general, universally-graspable version of the mechanism come first, with the specific study cited afterward as supporting evidence?
18. **Cover every text label in the diagram and look at the bare shapes alone: does each shape's own silhouette suggest the specific real object it represents, or is it a generic geometric primitive (plain rounded rectangle, plain circle, plain card) that could be relabeled as anything with no change to the drawing?** If a shape only reads as its object because of the words on or beside it, check it against failure mode 19 and add the one or two silhouette details (a ticket's punched tear-notch, a cup's handle, a receipt's torn edge) that a reader's eye actually uses to identify that object at a glance, placed at the object's most recognizable feature, not as decoration.
19. **Open one of the pilot diagrams (Loss Aversion, Halo Effect, or Goal Gradient) side by side and check: does the new diagram contain any `<rect>` (or other shape) wider than roughly 60px that wraps a whole row of content in a decorative background panel, rather than being a small icon shape?** If so, check it against failure mode 20 and rebuild as a single-column icon-plus-label chain directly on the `bg-*` field, with no enclosing panel — this applies regardless of which page the diagram lives on (principles.html, science-behind.html, or any future page reusing this pattern), and holds even if every other check above already passes.

## Building and presenting

- Match the real `.illustration` box spec from `mockup/principles.html` exactly: same dashed inset border, same `bg-terracotta` / `bg-mustard` / `bg-teal` / `bg-ink` class the placeholder already uses for that principle — so what's being reviewed is exactly what would ship, not an approximation. **As of the mobile-legibility redesign (failure mode 14), the box no longer forces a fixed aspect ratio** — `.illustration svg { display:block; width:100%; height:auto; }` lets each diagram's own `viewBox` set its rendered height, so use `<svg viewBox="0 0 400 {H}" width="100%" role="img" aria-label="…">` with **no `height` attribute**, where `H` is computed from the diagram's actual content (a single centered column: title, then two icon→label→arrow→outcome rows, then caption — see the `gen.py`/`icons.py` generator built for this rollout, worth reusing rather than hand-authoring coordinates again), not a fixed 300. The `aria-label` one-sentence summary of the mechanism is unchanged — still required, so the diagram is accessible even before anyone reads the caption below it.
- Use the site's real palette only, and get it from `mockup/styles.css`'s actual `:root` block immediately before drawing, not from memory or from a value recorded in this skill, `CLAUDE.md`, or an earlier conversation: as of this writing that's ink `#1B1E24`, terracotta `#C43E1F`, mustard `#E0A93A`, teal `#1F7A6C`, paper `#F5F6F5` — note these differ from the hex values recorded in the project's own `CLAUDE.md` (a stale record from an earlier palette revision), which is exactly the kind of drift that produced a diagram in the wrong colors once (see failure mode 19b). Pick the `bg-*` colour plus exactly one or two accents, and reserve the accent for *the mechanism itself* — the one thing the reader should look at first — never for pure decoration (borders, shading with no meaning). If an accent doesn't point at anything specific, it will score fine on visual interest and poorly on "digest quickly."
- **Text colour follows the `bg-*` class, not a fixed default.** The site's CSS gives `.bg-mustard` dark ink text (`#1E1B16`) because mustard is a light background; `.bg-terracotta`, `.bg-teal`, and `.bg-ink` all keep the default light/paper text (`rgba(251,249,244,0.95)`) because those three are dark backgrounds. Getting this backwards (light text on mustard, dark text on terracotta/teal/ink) is a legibility bug that won't show up in a structural check — only in the per-diagram screenshot.
- Pair icons with short text labels (dual-coding) so identification doesn't depend on either alone — and per failure mode 8, default to the icon-plus-concrete-label chain (linear chain or parallel rows — not fan converge/diverge, per failure mode 9) as the diagram's actual structure, not just a decoration added to an already-abstract chart.
- Package the set for review using the `design-options-review` skill's template — per-diagram rating buttons, a comment box, one "Copy feedback" button — so feedback comes back as clean, pasteable text instead of scattered chat replies.
- When a round's feedback triggers a redraw, keep a visible `round-tag` on the affected card and a short root-cause note (what was wrong, what was checked, what changed) rather than silently replacing the diagram — the review log is part of what makes the next round of feedback efficient.

## Production pipeline for shipping a batch of diagrams

The above is the per-diagram quality bar. This section is the mechanical process that shipped all 48 principle diagrams across six batches without any structural regressions — reuse it rather than improvising a new process each time a batch of principles needs diagrams.

1. **Extract exact citation data first, for every principle in the batch, before drawing anything.** Pull each principle's `id`, its `bg-*` class, and its citation's `excerpts` text directly from `mockup/principles.html` with a small Python/regex pass (`content.find('id="{pid}"')`, then find the `illustration bg-\w+` class and the citation block that follows). Write the extracted numbers/quantities down before designing — this is what the three-question check in the section above is actually checking against.
2. **Draw each diagram as a standalone `viewBox="0 0 400 300"` SVG string** matching the target principle's `bg-*` class and the text-colour convention above.
3. **Inject with a small, disposable Python script**, not by hand-editing a 4000+ line HTML file: regex-locate `id="{pid}"`, find the next `<div class="illustration bg-\w+"><span>Illustration placeholder</span></div>` after it, and replace just the `<span>Illustration placeholder</span>` with the SVG string. Print which ids were injected and which were missing (a missing id or placeholder means the principle's markup doesn't match the expected shape — investigate before moving on, don't silently skip it).
4. **Run a structural validation pass over the whole file** immediately after injection, before any visual review: count remaining `Illustration placeholder` occurrences (should drop by exactly the batch size), XML-parse every `<svg>...</svg>` block extracted via regex (`xml.etree.ElementTree.fromstring`) to catch unescaped `&`, unclosed tags, or malformed attributes, and confirm `<section class="principle"` / `</details>` counts are unchanged from before the batch. This catches injection-script bugs (wrong insertion point, corrupted markup) before wasting time on visual review of a broken page.
5. **Serve the directory locally** (`python3 -m http.server <port> --directory mockup`, launched with `nohup … &` — a bare backgrounded `&` inside a tool call that times out on exit code 144 kills the server with it) and screenshot **every diagram in the batch individually**: a small parameterized Playwright script that takes the principle id as an argument, force-opens that principle's `<details class="principle-details">` via `.evaluate("el => el.open = true")`, locates `.illustration` inside that section, scrolls it into view, and screenshots *that element* (not the page) at `device_scale_factor=2`. Loop it over every id in the batch rather than writing one bespoke script per principle. **Also required, per failure mode 14: a second pass in the same script at `viewport: {width: 375}` (real mobile width, no `device_scale_factor` zoom) that reads every `<text>` node's real `getBoundingClientRect().height` and flags anything under ~9px** — a 2x-zoomed desktop-width screenshot looks fine for text collisions but cannot tell you whether the text is actually large enough on a real phone; only the unzoomed mobile-width measurement can.
6. **Review each screenshot against the three-question check and failure modes 1–5** — fabricated/invented numbers, generic-object drift, unevidenced claims, text collisions, and divider lines bleeding through captions are all real bugs this exact pipeline has caught, batch after batch. Fix in the source HTML directly (targeted string replacement keyed on the principle's `id`, since ids repeat once per file), then re-screenshot just the fixed diagram to confirm before moving on — don't re-run the whole batch's screenshots to check one fix.
7. **Re-run the structural validation pass from step 4** after any fixes, then run a Playwright console-error check on the full page (open it, collect `console` events of type `error`) as a final gate.
8. **Commit with a message that names every principle in the batch and explicitly calls out any fabrication/legibility bugs caught and fixed during review**, not just "added diagrams" — the commit history is itself a record that the citation-fidelity check is actually being done, not skipped.

This pipeline is what "batch scale" means for this skill: it lets a set of 6–10 diagrams ship with the same per-diagram rigour as a single one, without the review step degrading as volume goes up.
