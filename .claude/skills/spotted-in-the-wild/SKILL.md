# Spotted in the Wild

## Why this exists

Founded 2026-08-26 on a direct request: a screenshot of GoDaddy's domain checkout, showing a "CHOSEN BY OVER 225,000 CUSTOMERS EACH MONTH" badge on an upsell, to be worked into the Social Proof principle article as a real, current example of the mechanism in the wild. The user's own framing: "This will become a skill we develop for each screenshot for behavioural articles uploaded and special reports etc." Every future screenshot should go through the same crop → locate → highlight-review → integrate pipeline, not a one-off process invented per image.

## What this content type is, and isn't

It's a **real, third-party UI screenshot** offered as a live instance of a mechanism already established by the article's own academic citation. It is not the evidence itself, the cited study (Salganik et al. for Social Proof, or whichever paper the target article already cites) is what proves the mechanism is real; the screenshot only shows a real company deploying it today. Never let a screenshot's caption imply it demonstrates the effect worked, a vendor's own "225,000 customers" badge is an unverified marketing claim, not a controlled measurement, and the honesty standard this site holds academic citations to (verified vs. paraphrased, sample size, method) applies here too: **a screenshot proves a tactic is in use, never that the tactic caused anything.** This is also distinct from `field-session` (personal photos of the owner's own talks and work) and `principle-mechanism-diagram` (an invented SVG diagram illustrating the cited study's own finding, not a real product).

## The pipeline, in order

1. **Crop out true chrome and any personal information, but keep real page context in.** True chrome is OS/browser furniture that carries no information about the product (an address bar, a share-sheet toolbar, a tab switcher): always safe to remove. Personal information (a name, address, account number, order ID tied to a real person) must always be removed, no exception, regardless of how much context it would otherwise add. Everything else, product name, price, what step of the flow this is, the button the user is about to press, is real context a reader needs to judge how the tactic sits inside an actual purchase, and defaulting to stripping it out for a "cleaner" image is a mistake this skill made on its own first real case: two screenshots were cropped down to just the isolated badge and rating line, and the result read as generic UI fragments with no way to tell they were real checkout screens at all. The user's own catch, verbatim: "you've taken too much of the screenshot away so context can't be seen." The fix was to re-crop from the original source with a far more generous frame, the full product/price header through to the actual payment button in one continuous, unedited region (skipping only true chrome and, on the personal-information screen, skipping the name/address block entirely by starting the crop below it rather than trying to redact and splice), then draw the same pixel-located highlight inside that bigger frame. When in doubt about how much surrounding UI to keep, keep more, not less; a highlighted claim floating in an otherwise-empty crop is what triggers this failure, not a highlighted claim sitting inside a recognizable, real screen. Check the final crop for any watermark or platform overlay per `CLAUDE.md`'s standing no-watermark policy either way.
2. **Locate the exact claim by pixel boundary, not by eye.** Before drawing any highlight, find the real pixel bounding box of the specific text or number being cited by scanning actual RGB values for the color transition between the claim's background (a badge, a highlighted row) and the surrounding page background, not by eyeballing coordinates off a scaled-down preview. A screenshot rendered to the model is not pixel-accurate to its saved file dimensions; sample real pixel colors in the actual saved file (Python + Pillow, scanning rows/columns for a color transition) to get an exact box, then pad it by roughly 8-10px for the highlight.
3. **Build five highlight-style options and let the user pick.** Default set, proven on the first real case, reuse these five unless the specific screenshot calls for something else:
   - **Clean outline** — a rounded-rect stroke around the claim, in the site's terracotta.
   - **Highlighter marker** — a semi-transparent mustard rectangle behind the text, mimicking a real highlighter pass.
   - **Spotlight, dim the rest** — everything outside the claim dimmed (ink at roughly 70-75% opacity), the claim itself left at full brightness with a thin outline. The most dramatic option; best when the claim is the entire reason the screenshot is being shown.
   - **Hand-drawn circle** — 2-3 slightly offset overlapping ellipses in terracotta, faking a sketchy hand annotation rather than a clean UI callout.
   - **Arrow + caption chip** — a small pill restating the number/claim in the site's own type, with an arrow pointing at the real text. Only works if there's genuine empty space near the claim to place the chip without covering other text; check this before committing to the layout, the first pass of this option covered the bullet list underneath and had to be repositioned into empty space beside the price column instead.
   Render all five as real images (not descriptions) inside this project's standard `oscarfinch-feedback-html` options-review template (binary toggle + comment per option, one copy-feedback button), per this project's own standing policy that any "options in HTML" request uses that template automatically.
4. **Wait for the pick, and expect a hybrid.** The first real case wasn't a straight pick of one of the five, it was "clean outline, use this, maybe add an elegant red arrow, not intrusive": the outline treatment plus a small, thin, single-color arrow (site's terracotta, ~3px stroke, short, no chip or label attached) pointing at the box from nearby empty space. Treat the five as a starting palette to combine, not five mutually exclusive final states. Route a request like this back through the same pixel-boundary discipline: find real clear space near the box (verify it's actually background-color, not text, by sampling pixels) before placing the arrow, and keep the arrow short and thin enough that it reads as a pointer, not a second highlight competing with the outline.
5. **Finalize and save.** Save the chosen image to `mockup/images/` with a descriptive filename following the site's existing convention (`source-context-slug.jpg` or `.png`, lowercase, hyphenated, e.g. `godaddy-domain-protection-social-proof.png`), not a generic name.
6. **Integrate as a new "Spotted in the wild" block** inside the target article's `article-body`, positioned after the existing `.article-block`s (psychology / errors / help) and before the `.study-card`, so the reader meets the mechanism explanation and the real citation first, then sees it deployed live, then reaches the academic proof. Use the `.spotted-wild` CSS component (`styles.css`): a bordered card matching `.study-card`'s tokens, holding one shared intro sentence, a `.spotted-grid` (2 columns on desktop, 1 on mobile via a 640px breakpoint) of `.spotted-item`s when there are multiple screenshots from the same real flow, each with its own `.spotted-caption`, and one shared closing `.spotted-disclosure` at the end rather than repeating the honesty caveat per image, when every image in the block comes from the same source and date. Caption format, every time: what the real product/company is, the exact quoted claim, the date captured. The vendor's-own-unverified-claim caveat can live once in the shared `.spotted-disclosure` for a multi-image block, or per-caption for a single-image block, but it must appear somewhere in the block every time, it's the load-bearing honesty check for this whole content type.

## Two mechanical gotchas found while building the first real block

- **A screenshot rendered inline to the model is not pixel-accurate to its saved file.** Coordinates read off the displayed image will be off; always reload the actual saved file and scan real pixel values before computing any box or clear-space check, per step 2 above. This bit twice: once finding the badge's true boundary, once discovering a "clear" area next to a badge was actually still inside the card's off-white background rather than the page's slightly different off-white, requiring a second, finer pixel scan to find the real transition point.
- **A tightly-cropped screenshot (little margin around the content) breaks the "spotlight" and "hand-drawn circle" options and needs a wider canvas for anything drawn outside the existing frame.** On the second screenshot in the first real case (a two-line ratings badge filling almost the entire crop), spotlight lost its dramatic effect (nothing left to dim), and the circle's sketchy wobble grazed the surrounding text at the edges because there wasn't enough real margin to wobble into. When a highlight needs to extend beyond the tightest reasonable crop (an arrow with clearance, a circle with real breathing room), re-crop from the *original* source image with extra padding on the relevant side rather than padding the already-cropped file, and when programmatically cropping a working image to trim empty space back down afterward, clamp the crop bounds to the image's actual dimensions, `Image.crop()` silently pads out-of-bounds regions with solid black instead of erroring, which shipped once as an unexplained black bar at the bottom of a finished image before it was caught by re-viewing the file.
- **When personal information sits between two regions you want to keep, don't redact or splice, just start the crop after it.** A real order-summary screenshot had a name and home address between the header and the rest of the page worth keeping. Compositing two non-adjacent regions together to skip the middle leaves a visible seam and looks edited, which undermines the whole point of showing something authentic. Instead, find the exact pixel row where the personal-information block ends (the same pixel-scan technique as locating a highlight box) and crop the single continuous region starting a safe margin below that row. The result is still one unedited, contiguous real screenshot, just missing its very top portion, which reads as an honest crop, not a doctored one.

## Failure mode: the personal-information rule was written down and still didn't get checked

**What happened.** Two images already live on the site (`proper-cloth-complimentary-remake.jpg`, a Science Behind screenshot, and `commbank-home-loan-appointment-confirmed.jpg`, an Experiments screenshot) had a staff name and a phone number blurred, per this skill's own rule, but nobody actually checked the rest of each image for other identifiers. `proper-cloth-complimentary-remake.jpg` had two full order numbers (`AC1298920A`, `AC1292270A`) sitting in plain, high-contrast text one line below the blurred name, unredacted, for days, on the live site. `commbank-home-loan-appointment-confirmed.jpg` had a mobile number masked to only 5 of its 10 digits (`04** *** 400`), leaving the area code and last three digits, which is a partial redaction, not a real one. The rule ("Personal information... must always be removed, no exception") was already written in this skill before either image shipped. It was applied to the one identifier that was easy to spot (a name in a sentence) and not applied as an exhaustive scan of the rest of the frame. A person's eye catches a name; it does not automatically catch a reference-code-shaped string sitting in a product heading, because it doesn't read as "personal information" the same way a name does.

**The check, going forward.** Treat "remove personal information" as a full-frame scan for a category of thing, not a single find-the-name pass. Before finalizing any crop, look specifically for: order numbers, confirmation numbers, reference numbers, account numbers, tracking numbers, invoice numbers, booking references (anything alphanumeric that looks like `AC1298920A` or `#4471829`, whether or not it's labelled), phone numbers (full or partial), email addresses, physical addresses, and dates of birth. A masked value counts as fixed only if the masking removes enough of the string that the remaining fragment can't narrow down the full value in practice, for a phone number that means redacting the whole number, not leaving the area code and last few digits visible, since that's a small enough remaining search space to not count as anonymised. When redacting text found this way (as opposed to a name inside a sentence, where cropping above/below the line usually works), locate the string's real pixel bounding box the same way this skill already locates a highlight target (scan real RGB values in the saved file, not the rendered preview) and paint over it with a rectangle matching the surrounding background colour, padded a few pixels on each side, rather than trying to blur it (a solid fill is unambiguous and doesn't risk a recoverable blur).

**Do this scan on every image before it's saved to `mockup/images/`, not just once at launch.** This applies retroactively too: when a new personal-information category is identified (as order numbers were here), it's worth a quick pass over every existing "spotted in the wild" image already on the site, not just future ones, since the failure is exactly that a real, identifiable item can sit on a live page for a while before anyone notices it wasn't actually covered by the rule everyone assumed was already being followed.

**A third gotcha found while fixing the first two: a partially-hidden identifier under other UI chrome still counts.** `proper-cloth-complimentary-remake.jpg` had a *third* order number in the same image, one row of an order-summary table sitting almost entirely behind the screenshot's own black nav bar, with only the rounded bottom tips of its digits (in link-blue) poking out below the bar by a few pixels. Rendered small, this reads as a meaningless thin blue line, easy to dismiss as a UI border or anti-aliasing artifact rather than clipped text, which is exactly how it survived the first redaction pass. The check: when a full-frame scan turns up any sliver of colored or dark pixels running along a hard edge (a nav bar, a card boundary, a cropped panel), crop and zoom that exact sliver at 2-4x before deciding it's decorative. Redact it even if the remaining fragment looks illegible after zooming in, since "probably not readable" is not the same bar as "removed," and the cost of painting over a few stray pixels of true chrome is zero.

## Failure mode: real evidence lands on Science Behind and never gets mirrored back to the principle it illustrates

**What happened.** A Science Behind entry names its cited principles via `.sb-chips` and links each mechanism block back to `principles.html#<slug>`. When that entry also carries real photographic evidence for a mechanism (a `.spotted-wild` block or an inline `.sb-screenshot`), the principle article on the other end of that link kept using only its own invented, abstract SVG diagram, never the real photo one click away on the same site. The Framing Effect principle is the clearest case: it already cross-linked to `macca-golden-deal`, a Science Behind entry with two real McDonald's screenshots, but the principle page itself showed only a hand-drawn beef-labelling diagram. The owner's catch: "I've shared good real life example screenshots of framing. They should be used to illustrate." A site-wide check found seven more principles with the identical gap (loss-aversion, clawback, mental-accounting, goal-gradient, chunking, scarcity, probability-weighting), all citing `up-bank-teardown` or `macca-golden-deal`, entries that already had the exact real image each of those principles needed, sitting unused behind a citation link instead of shown inline. Two Science Behind entries (`proper-cloth-and-son-of-a-tailor`, `up-bank-teardown` for several of its own mechanisms) and `bankwest-interesting-rate` also cite principles that don't yet mirror their evidence either; run the check below before assuming a given principle is clean.

**The check.** `scripts/check_missing_wild_mirror.py` (run from the repo root, no arguments) cross-references every principle's "Decoded on The Science Behind" links against the Science Behind entries they point to, scoped to the *specific* `.sb-block` the citation sits inside (an entry with photos for 2 of its 7 mechanisms shouldn't flag the other 5). It flags any principle that cites a mechanism with real evidence but has no `.spotted-wild` block of its own. Run it before calling any new principle, or any new Science Behind entry that adds evidence to an existing mechanism, finished.

**The fix, in practice.** This doesn't require a new photo shoot or the full crop-and-highlight pipeline again: the image is already processed, already captioned once, already living in `mockup/images/`. Reuse the exact same file on the principle page, in a new `.spotted-wild` block positioned the same place Science Behind puts it (after the `.article-block`s, before `.study-card`), with a caption and disclosure line written fresh for that principle's own framing, not copy-pasted verbatim from the Science Behind entry (the same image can honestly support two slightly different captions: Science Behind's caption serves the object being decoded, the principle's caption serves the mechanism being taught). A principle citing multiple entries with only one real image between them (e.g. one entry, one screenshot) gets a single `.spotted-item.single` block per the two existing single-image precedents (`diversification-heuristic`, `ambiguity-aversion`); a principle whose Science Behind entry shows two related screenshots together (like `macca-golden-deal`'s pair) gets the two-column `.spotted-grid` instead, matching whichever shape the source entry itself used.

## Failure mode: "keep more context" turned into a raw, disproportionate dump

**What happened.** The McDonald's screenshots for `macca-golden-deal` (and later mirrored onto `framing-effect` and `probability-weighting`) were cropped exactly per this skill's own "keep more context, not less" rule: the full page from nav bar down through the target paragraph, one continuous, unedited region. Taken literally on a page with a huge decorative hero graphic between the nav and the actual claim, that produced a 1179×1820px image where the real content, one heading and one paragraph, occupied under 25% of the frame, with a large low-information hero banner and dead vertical space in between. Rendered at typical container widths, the highlighted phrase sat far down a long, mostly-decorative scroll, and the image carried no explanation of what it was if seen without its separate HTML caption underneath. The owner's catch, verbatim: "Images all out of proposition... They should be better collages. Not just a pure dump. They should also be a bit annotated so self contained." The context rule was never wrong, "more context" was misapplied as "the entire unedited page," when the actual goal was always a reader understanding the claim at a glance, not a literal full-page capture.

**The check.** After building a crop, before highlighting anything, ask what fraction of the frame is genuinely load-bearing (the heading, the paragraph, the badge, whatever states the actual claim) versus decorative or structural filler (a hero banner, a big product photo, generic nav chrome, dead vertical whitespace between sections). If the load-bearing content is under roughly half the frame, that's the signal to compose a collage instead of shipping one continuous crop, not to crop even more context away (which is the opposite failure this skill already warns against) or to leave it as is.

**The fix, in practice.** Build the image as a genuine composed collage, not a single continuous crop, in three parts:
1. **A shrunk, small representative crop of the decorative/brand element** (the hero banner, the product shot), resized down to a fraction of its original height and centered, kept for brand-recognition and authenticity, not shown at full size. This is different from cropping it out entirely (a screenshot with zero brand context reads as a generic UI fragment, the exact failure the "keep more context" rule already guards against); shrinking keeps the recognition value while removing its disproportionate share of the frame.
2. **A full-size, uncompressed crop of the actual claim**, heading and paragraph, with the existing highlight-box treatment drawn on it exactly as before.
3. **A top annotation label bar** (site ink background, white bold text, the real source stated plainly: "REAL McDONALD'S AUSTRALIA APP SCREEN, SEPT 2026") composited above both, so the image is self-contained even seen on its own, without relying on the separate HTML caption below it to say what it is. No em dash in this label text either, same standing site policy, write it as a plain, comma-free label instead.

Stack these three pieces vertically with PIL (`Image.new` + `.paste`, no gaps between pieces so there's no dead space to reintroduce), redraw the highlight box on the claim crop using the same pixel-located coordinates minus that crop's own offset, and save over the same filename. Since `mockup/*.html` references the file by its real pixel dimensions (for the anchor-scroll CLS fix, see `CLAUDE.md`'s standing image-dimension policy), **update every `width`/`height` attribute referencing that filename to the new composed dimensions** wherever the image is used, not just the one place the defect was first noticed; grep the filename across every `mockup/*.html` file rather than trusting memory of where it's used.

**A second, unrelated defect found while rebuilding these two images.** One source screenshot's paragraph text ran flush to the frame's exact right pixel edge with zero margin, and a real iOS scroll-thumb indicator happened to be captured mid-fade sitting directly on top of one word. Padding the *outside* of that crop does nothing, the text was already touching the crop's inner boundary in the source file itself, so there was no hidden margin to reveal. This is a source-material limitation, not a cropping mistake, distinguishable from an actual bad crop by re-cropping the raw original slightly differently and checking whether the same character is still missing (if it is, it's the source, not the crop). Leave it rather than trying to manufacture pixels that were never captured, so long as the affected word isn't inside the highlighted claim itself.

## Failure mode: revising an already-shipped image under the same filename looks unfixed to a cached browser

**What happened.** After the collage rebuild above shipped and was confirmed live (`curl` against the raw image URL showed the new, correct file with a fresh `last-modified` timestamp), the owner reported "Same issue" with a screenshot showing the old, un-collaged layout, no label bar, full-size hero graphic. The server-side content was genuinely correct; the browser that took the screenshot was showing a stale, already-cached copy of the image bytes from before the fix, because the fix reused the exact same filename and URL. GitHub Pages serves images with a 10-minute edge cache (`max-age=600`), and a phone's own browser image cache can hold on to a previously-loaded image well past that until something forces a real re-fetch, a plain page reload often isn't enough for an already-cached image resource specifically, even when the surrounding HTML reloads fine.

**The check.** Before telling the owner an image fix is live, verify server-side with a fresh, uncached request, `curl` the raw image URL directly (not the HTML page) and check its `Content-Length` and `Last-Modified` header against the file just committed, or decode and inspect the fetched bytes directly. If that confirms the new file is being served, and the owner still reports the old version, the fault is client-side caching, not a shipping mistake, and the fix is a cache-bypass, not another content edit. Don't re-edit an already-correct image because a screenshot still shows the old one; that wastes a revision cycle on a problem that isn't in the content.

**The fix, in practice.** State plainly that the live file is confirmed correct (cite the verification: the direct URL fetch, the timestamp), and ask the owner to force a real reload of that specific image, a hard refresh or reload of the page (not just re-opening the same tab), or closing and reopening the tab, since a normal pull-to-refresh sometimes still serves cached sub-resources. If this keeps recurring on an image that gets revised more than once in a short window (exactly the case here, three revisions to the same two filenames in one session), consider a harder cache-bypass: append a throwaway query string to the `src` temporarily (`file.jpg?v=2`) to force every client to treat it as a new resource, then remove the query string once the owner has confirmed the fix looks right and normal caching resumes being harmless.

## Failure mode: dismissing a real screenshot as "redundant," and stopping the scan at the first thing found

**What happened.** Of the three real McDonald's screenshots the owner originally shared, one (a clean, well-composed promotional card: logo, food array, "Learn more") was judged "redundant, doesn't mention 'free Macca's for life' directly" and dropped from the pipeline entirely, in favour of a busier, messier full-page hero photo that happened to contain the exact target phrase. And in the McGold Card screenshot, the pixel scan stopped once "The McGold Card" heading and its paragraph were located, the crop was finalized from there without ever scrolling further down the same file, even though the file's own real height (2346px) extended another thousand pixels past the crop boundary used. That remaining space held a second real card graphic, the Silver Card, the exact second prize tier the site's own text already cited ("8 McGold Card and 40 Silver Card winners") but had never actually shown. The owner re-sent the exact same three files and said, plainly, "You need to start by getting these screenshots and putting them into a collage." Two separate judgement calls were both wrong in the same direction: cut material too early, on both a "which files matter" pass and a "how far into this one file does real content go" pass.

**The check.** Before dropping an uploaded screenshot as redundant, ask what it shows that the others don't, cleaner production art, a different angle, a detail the messier version buries, not just whether it contains the one exact phrase already found elsewhere. A screenshot that doesn't repeat the target quote can still be the better visual to build the collage around. Separately, before finalizing any crop, scan the *entire* height (or width) of the source file, not just down to wherever the first relevant heading and paragraph were found; a long screenshot capturing a real scrolling page routinely contains more than one real, citable thing, and stopping the pixel scan at the first hit silently discards whatever came after it.

**The fix, in practice.** Rebuilt both collages using material from all three original files: the clean promotional card (previously dropped) replaced the busy hero photo as the "what the deal looks like" panel, and the previously-uncropped Silver Card graphic, sitting later in the same McGold Card screenshot, was added as a genuine second element with its own caption, upgrading the entry's own sourcing note from claiming only the McGold Card's existence to confirming the Silver Card's existence too, directly from the primary source. Before calling any spotted-in-the-wild image set finished, re-open every uploaded file (not just the ones already used) and check each one top to bottom, or full width, for anything not yet captured, rather than treating "I already found something usable" as a reason to stop looking.

## Voice and rigor, same as everywhere else on the site

- **Never let the caption blur "a real company uses this tactic" into "this tactic worked here."** The cited academic study is the site's evidence; the screenshot is an example of deployment, always phrased that way.
- **No em dashes.** See `CLAUDE.md`'s standing policy.
- **No watermarks.** Check every screenshot before it reaches `mockup/images/`, the same standing policy that applies to every other image on the site.
- **Identify the named company if it isn't a household name**, per the identification rule already established in `science-behind-article`. A brand like GoDaddy is recognisable enough to skip this; a smaller or less familiar one needs a one-clause identification before the caption uses its name again.
